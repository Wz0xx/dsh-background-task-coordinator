## 一、这次修掉的三处真问题

### 1. 缺的不是注册表，是控制层

第一次以为是 `@deepseek-ai/dsh-jobs-local` 没挂，加进去报：

```
Error: service "jobs" has been registered at <LocalJobRegistry>
```

——注册表本来就在宿主层，一次注册服务所有会话。

真正缺的是 **`@deepseek-ai/dsh-tool-jobs`**，它才是 `attachController` 的那一层；它原先只挂在 `~/.dsh/.agent-presets/redteam/agent.cordis.yml` 里，家会话没有。依据就在那个文件的注释里：

> The registry is keyed by owning agent anyway, so one host instance serves every session. What a preset chooses is whether its agent can collect and stop background work at all.

补进 profile 的 `cordis.patch.yml` 后，`task_create(type=job)` 从 `no job controller serves this agent` 变成可以启动。

### 2. Job 适配层是按 README 猜的，与真实契约不符

| 代码里写的 | 真实契约（cordis inspect → Service.jobs） |
|---|---|
| `start({command, args, name}, owner)` | `start(spec)`，owner 在 `spec.owner` |
| — | `spec.kind` 必填，`JobKindMap = { bash: 'bash' }` |
| — | `run(job)` 返回 `{ cancel(reason?), done: Promise<JobOutcome> }` |
| `readAt` 返回 `text` | 返回 `{ chunks, next, lossy }` |
| `kill(id, reason)` | `kill(id, caller?, reason?)` |
| `events.on('settled', cb)` | `events.subscribe({ owner } \| { owners: 'all' \| 'scope' }, cb)` |
| `state: done/failed/cancelled` | `status: completed/killed/failed/running/stopping` |

少了 `kind` 时，注册表在 `spec.kind.length` 上抛 `TypeError`。

### 3. subagent 的结算没人接

台账里 subagent 任务永远停在 `running / delegated`，而原生 agent 早就结束了。

真源在事件上，不在轮询上：

```
'subagent/end'(this: Scoped<SubagentRuntime>, info: SubagentRunEndInfo): void
```

`info` 里有 `id`（= sessionId）和 `stopReason`。订阅它之后，台账自动落到 `completed`。

### 附：两个次要的

- **子进程输出是 GBK**，直接 `String(buffer)` 是乱码。改成先按 UTF-8 严格试解、失败转 GBK 并记住。
- **`child.kill()` 只杀 cmd.exe，不杀它下面的进程**。取消后台账标 `cancelled`、`ping` 还在跑。改成 `taskkill /T /F /PID`（按进程树杀）。

## 三、完成情况

**十二项全部通过**（2026-11-25 收口）。过程中修掉的真问题：

1. **`ctx.jobs.start` 契约**：不是 `start({command,args,name})`，是 `start({kind:'bash',label,run(job)})`，同步返回 JobId；`readAt` 返回 `{chunks}` 不是 `text`；`kill(id, caller, reason)`。原先按 README 猜，在 `spec.kind.length` 上抛 `TypeError`。
2. **取消只杀 cmd.exe**：`shell:true` 下 `child.kill()` 杀不掉孙进程，`ping` 还在跑。改成 `taskkill /T /F /PID` 按进程树杀。
3. **中文输出乱码**：子进程吐 GBK，先按 UTF-8 严格解，失败退 GBK 并记住。
4. **结算回调收不到**：协调器原先只在 `start()` 时订阅已有 owner，新建 owner 的 job 永远收不到结算。改成 `createTask` 分派成功后补订阅。
5. **追加指令把子代理打成 error**：`steer`/`followup` 收消息对象不是字符串（T06 两次失败的根因）。
6. **重启后虚报 running**：`ctx.agents.get()` 对已结束的 agent 返回 undefined，区分不了「完成」和「中断」。加了启动对账：原生执行单元不存在就标 `interrupted`。

仍保留的空白（都不影响使用）：

- **Mode A（插件侧直创 subagent）**：`spawnChild` 仍是抛错桩。现在走 Mode B（模型侧 `subagent` 建 + `task_register_delegation` 绑），已经够用；真要让协调器自己 spawn 再启用。
- **任务类型自动识别、composite 编排（任务书阶段 3）**：有意不做。人一句「放后台」比模型猜得准，写出来是白写。
