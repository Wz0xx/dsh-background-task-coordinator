## P0-1 沙箱 100% 绕过 —— 已修，并改成 fail-closed

**改前**：

```js
try {
  const policy = exec?.agent ? await ctx.sandboxPolicy?.resolve?.({session: exec.agent.session}) : null;
  if (policy && policy.mode !== 'danger-full-access' && typeof ctx.sandbox?.confine === 'function') {
    const sandboxed = await ctx.sandbox.confine(wrapped, policy);
    if (Array.isArray(sandboxed?.argv) && sandboxed.argv.length) wrapped.splice(0, wrapped.length, ...sandboxed.argv);
  }
} catch (e) { /* 拒绝 */ }
// ↓ 然后
const child = spawn(parts[0], parts.slice(1), { shell: true, windowsHide: true, cwd });
```

问题不止「没用 wrapped」：
- `exec.agent` 为空 → 整段跳过 → 直接裸跑
- `policy` 为 null → 跳过 → 裸跑
- `confine` 不存在 → 跳过 → 裸跑
- `confine` 返回空 argv → 跳过 → 裸跑

四条都是 **fail-open**：不知道该怎么限制时，默认放行。

**改后**：

```js
let argv = null;
try {
  const policy = ag ? await ctx.sandboxPolicy?.resolve?.({session: ag.session}) : null;
  if (!policy) { /* 落 failed，拒绝 */ }
  if (policy.mode === 'danger-full-access') {
    argv = wrapped;                       // 宿主明确允许
  } else {
    if (typeof ctx.sandbox?.confine !== 'function') { /* 落 failed，拒绝 */ }
    const sandboxed = await ctx.sandbox.confine(wrapped, policy);
    if (!Array.isArray(sandboxed?.argv) || !sandboxed.argv.length) { /* 落 failed，拒绝 */ }
    argv = sandboxed.argv.map(String);
  }
} catch (e) { /* 落 failed，拒绝 */ }
// ↓
const child = spawn(argv[0], argv.slice(1), { shell: false, windowsHide: true, cwd, detached: ... });
```

四个分支全部改成「不确定就拒绝」。`shell: false` 因为 argv 已是完整命令行
（`['cmd.exe','/d','/s','/c', 原文]` 或 confine 给的形式），再开一层 shell 会二次解析。

**验证**：mock 的 `confine` 返回 `['echo','CONFINED_ONLY']`，
确认调用发生了，且拿到的 argv 是完整命令行 —— 不再走 `parts`。

## P0-2 未解析 session id 形成永生僵尸 —— 已修三条路

**改前**：

```js
// 重启对账
alive = t.nativeSessionId ? !!getAgentHandle(ctx, t) : true;   // ← 恒真
// sweepOnce
if (... || !t.nativeSessionId) continue;                       // ← 直接跳过
// 超时清账
if (t.type === 'job' && ...)                                   // ← 只对 job
```

三处叠加的后果：`nativeSessionId=null` 的任务在**所有清理链路里都被豁免**，
永远停在 ACTIVE，累积到 `perOwner=2` 就锁死配额，只能删库。

**改后**：

1. **重启对账**：`alive = t.nativeSessionId ? !!getAgentHandle(ctx, t) : false`。
   重启意味着上一个进程内的 agent 全没了；没有 session id 就无法重新接上 ——
   这种任务应该落 `lost`，而不是假装活着。

2. **sweepOnce**：不再跳过。没 session id 的走「宽限期」：
   超过 `timeoutMinutes` 还没绑定，就当失联收掉。宽限期内不动（正常登记流程中）。

3. **超时清账**：对 subagent 追一次探活，原生不在就直接落 `lost`。

4. **task_cancel**：subagent 没有可中断对象时，直接落 `cancelled` 收尾，
   不再只写 `cancel_requested` 然后等一个不会来的事件。

## P0-3 跨会话越权（Confused Deputy）—— 已加归属校验

**改前**：7 个业务工具**零归属校验**，且 `task_cancel` / `task_describe` 把
`row.ownerSessionId` 冒充成 `caller` 传给 `ctx.jobs`。

后果：任意群聊会话或受提示注入的子代理，只要 `task_list` 拿到 taskId，就能
偷看私聊 job 输出、篡改别人的上下文、往别人的子代理注入指令、直接杀别人的任务。
**而 DSH 0.2.2 特意加的 `assertAccess` 围栏被这个冒充穿透了。**

**改后**：

新增两个 helper：

```js
function callerSessionId(exec) {
  const ag = exec?.agent ?? null;
  if (!ag) return null;
  return String(ag.id ?? ag.session?.id ?? '');   // 两处都认
}
function ownedBy(row, exec) { /* owner 为空放行；caller 拿不到放行但不冒充；两者不等拒绝 */ }
```

所有 7 个工具都接 `exec` 并校验：

- `task_describe` / `task_append_message` / `task_cancel` / `task_context`：
  不匹配直接返回「任务不存在」（不泄露它存在与否）
- `task_list`：只列自己的
- `task_cancel` 调 `jobs.kill` 时传**真实 caller**，不再用 `row.ownerSessionId` 冒充

**验证**：`sess-B` 取消 / 查询 `sess-A` 的任务 → 均被拒；`sess-A` 自己操作 → 成功。

## P1-1 `perOwner` 限额按 `conversationId` 统计 —— 已改按 `ownerSessionId`

**改前**：`mine = activeAll.filter((x) => x.conversationId === conversationId)`

`conversationId` 是模型可控参数，默认字面量 `'current'`。后果双向：
- 正常调用时所有会话挤同一份额度 → 全局上限 3 形同虚设
- 单会话随便传不同 `conversationId` 就能绕过 `perOwner`

**改后**：按 `ownerSessionId`（真实会话）统计。

**验证**：同一 owner 传 4 个不同 `conversationId` → 第 3、4 个被拦（made=2 blocked=2）。

## P1-2 spawn 未接 error / 进程树泄漏 —— 已修

- **`child.on('error')`**：不接住的话，cwd 被删、权限不足、进程数上限都会让
  Node 抛未捕获异常，**直接打崩 DSH 宿主**。现在接住、写进 job 输出、并让 `done` 收口。
- **`done` 悬空**：spawn 失败时 `close` 可能永不触发。现在同时监听 `error` 解析 `done`。
- **`close` 第二参 signal**：被信号杀掉时 `code` 为 null，以前报「exit null」。现在写 `killed by SIGKILL`。
- **非 Windows 进程组**：以前只 `child.kill('SIGKILL')` 杀父 shell，子孙全泄漏。
  现在 `detached: true` + `process.kill(-pid, 'SIGKILL')` 整组杀。

## P1-3 `task_cancel` 对 subagent 是空操作 —— 已修

**改前**：`nativeOk = 'interrupt-requested(经模型工具)'` —— 只是给变量赋了个字符串，
**既没调 `ag.cancel()` 也没调 `ctx.subagents.interruptByParent()`**。
模型看到「已请求取消」就不会再动手，子代理照常跑完并产生全部副作用。

**改后**：真调 `ag.cancel({kind:'user'}, {keepInbox: true})`；无可中断对象则直接落终态。

**改前**：8 KB 上限把 `row.objective` 也算进去。objective 只要超过 8 KB，
`task_context` 就永远报超限、完全不可写（哪怕只写一个 stage）。

## P2-8 限额参数无校验 —— 已加

`NaN` 会让 `length >= NaN` 恒 false（限额失效）；`sweepSeconds` 为 NaN 会让
`setInterval(fn, NaN)` 退化成 1ms 死循环。现在 `num()` 校验，非法值回落默认。

## 未做（写清楚，不假装做了）

1. **`LIMIT 500` 硬截断**（P1-4）。仍是全表拉 500 条内存过滤。
   影响：任务数超过 500 后，新任务可能掉出窗口 → 结算事件丢弃。
   要做需要改 `listTasks` 加 `findActiveByNativeId` 之类的定向查询 + 建索引。
2. **`purgeHistoryOlderThan` 从未调用**。历史无限增长，加剧上一条。
3. **`task_messages` 幂等键是全表 UNIQUE 而非 `(task_id, key)`**（P1-7）。
   跨任务复用显式键时，B 的投递会写库失败但消息已发出。
4. **`pending` 消息不 flush**（P1-5）。绑定前的追加消息永久卡在 pending。
5. **`makeChunkDecoder` 三重乱码缺陷**（P2-6）。首包 ASCII 就锁死 utf8，
   GBK 中文全乱。要做需要单流 decoder + `{stream:true}`。
6. **多 profile 共享单库**（P2-7）。第二个 profile 启动对账会误判第一个的活任务为 lost。
7. **`settleNotification` 只记账不投递**（P2-9）。`lost` 等协调器自产的终态，
   事件流水写「通知已入账（原生通道送达）」，实际前台收不到任何东西。**这条措辞是错的。**
8. **`stopReason` 只认 cancel/fail/error/abort，其余全判 succeeded**（P2-2）。
   `max_turns`、`timeout`、空字符串都会落 `succeeded`。
9. **`Singleton` 生命周期**：`dispose()` 不关 `_sqlite`，热重载会翻倍订阅。
