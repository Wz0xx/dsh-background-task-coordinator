# 0.1.5 改动记录（2026-11-27）

对应反馈：《subagent 任务跑完，台账永远停在 running》、兼容层整合方案 P0/P1/P2/P3。

## 一、修掉的三条真 bug

### 1. `subagent/end` 匹配漏字段（`index.js` 事件订阅）

**改前**：
```js
const t = d.listTasks({ limit: 500 }).find((x) => x.nativeId === String(id));
```
只比 `nativeId`（存 agent 名）。事件里的 `id` 是会话 id，两边永远不相等 → `if (!t) return;` 静默返回 → 台账永远 `running`。

**改后**：
```js
const sid = String(id);
const t = d.listTasks({ limit: 500 }).find(
  (x) => x.nativeId === sid || (x.nativeSessionId != null && x.nativeSessionId === sid),
);
```

**依据**：`@deepseek-ai/dsh-subagent/types` 的 `SubagentRunEndInfo` 原文只有
`{ runId, provider, id: SessionId, local, stopReason, lastAssistantMessage? }`，
没有 `sessionId` / `agentId` / `childId`（本机 asar 提取）。

### 2. `task_register_delegation` 把名字当会话 id（`index.js`）

**改前**：
```js
nativeId: String(args?.agentId ?? ''),
nativeSessionId: String(args?.sessionId ?? ''),
```
原生 subagent 工具只回 `started subagent <name>`，调用方拿不到会话 id，
只能把名字填两遍 —— 于是 `nativeSessionId` 里存的是名字。

**改后**：`execute(args, exec)` 拿 `exec.agent` 作 caller，调
`resolveSubagentSessionId()` 双路反查，反查不出就留 `null`：

```js
const realSid = await resolveSubagentSessionId(ctx, agentName, exec?.agent, String(args?.sessionId ?? ''));
d.updateTaskFields(tid, {
  status: 'running',
  nativeId: agentName,
  nativeSessionId: realSid ?? null,
  ...
});
```

返回文本按成败分两种措辞（解析成功带出会话 id；失败明说「结算靠兜底」）。

### 3. 三处 `ctx.agents.get(agent 名)`

`ctx.agents` 只按 session id 索引，喂名字必然 `undefined`。

| 位置 | 改前 | 改后 |
|---|---|---|
| `task_describe` 探活 | `ctx.agents?.get?.(t.nativeId)` | `getAgentHandle(ctx, t)` |
| `task_append_message` 投递 | 同上 | 同上 |
| 启动对账探活 | 同上 | `t.nativeSessionId ? !!getAgentHandle(ctx, t) : true` |

**第三处特别注意**：若 `nativeSessionId` 为 `null`（没解析出来），不能判 `lost`
——那是「不知道」，不是「死了」。只有解析出 id 的才按探活结果判断。

## 二、新增 `compat/subagents-adapter.js`

名字 → 会话 id 双路反查 + 能力探测。

### 双路逻辑

| 宿主版本 | 路径 | 依据 |
|---|---|---|
| 0.2.2+ | `ctx.subagents.resolveName(caller, name)` | 反馈人实测 |
| 0.2.1 | `ctx.subagents.listChildren(parentSessionId)` → 按 `label` 匹配 | 本机 asar：`SubagentCatalogEntry = { id, createdAt, mode, label? }` |

**本机 0.2.1-rc.4 没有 `resolveName`**——asar 里 5 处命中全是 fast-xml-parser
的私有 `_resolveName`。`subagents` 服务键本身在 0.2.1 已注册
（`TeamService.inject` 里就有 `'subagents'`），所以降级路径成立。

### 不把名字当 id 的三道闸

1. `resolveName` 对非名字 token 会原样返回 → `String(sid) !== name` 才采用
2. 调用方传的 `sessionId` 若等于 `agentId`（说明是名字）→ 不采用，走反查
3. 全部路径失败 → 返回 `null`，落库为 `null`

### 单元验证（10/10 通过）

- 0.2.2 路解析出真 id
- `resolveName` 原样返回时判为未解析
- 0.2.1 路按 `label` 找到
- 同名多个取最新
- 无服务返回 null（不把名字当 id）
- 调用方给真 id 时直接采用
- `sessionId` 传名字时不采用、走反查
- 能力探测三种组合全对

## 四、P2 启动自检（`compat:` 一行）

启动时输出能力三态：

```json
{"overallStatus":"degraded","missingRequired":[],"degraded":["subagent.resolve_name","subagent.list_children","subagent.settle_resolve"],
 "caps":{"job.start":"supported","job.inspect":"supported","job.cancel":"supported",
         "job.settle_event":"supported","job.activity_event":"supported","agent.get":"supported",
         "subagent.resolve_name":"unsupported","subagent.list_children":"unsupported",
         "sandbox.confine":"supported","sandbox.policy":"supported",
         "working_directory":"supported","system_prompt.section":"supported",
         "subagent.settle_resolve":"unsupported"}}
```

判定规则（任务书 §9）：
- 必需能力（`job.start` / `job.inspect` / `job.cancel` / `agent.get`）缺失 → `incompatible`
- 只有可选能力缺 → `degraded`
- 全绿 → `compatible`

**只做反射检测**，不起真实任务、不发消息（任务书 §16）。
