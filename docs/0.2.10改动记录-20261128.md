## Bug 1：沙箱分支里带引号的命令会退化

### 报告说的

> `echo "a b"` 输出 `\"a b\"`，`powershell -Command "..."` 只回显不执行。

### 我自己复现了

`草稿/q-verbatim.mjs`，同一条命令两种交付方式对照：

```
[A. 原文直传]  verbatim=false
  argv 尾部: "echo \"quoted ok\""
  stdout:    "\\\"quoted ok\\\""        ← 反斜杠进了输出

[C. powershell 原文]  verbatim=false
  argv 尾部: "powershell -NoProfile -Command \"Write-Output 42\""
  stdout:    "Write-Output 42"          ← 只回显，根本没执行
```

**第二个例子比报告写的还严重**：不是引号多俩反斜杠，是命令完全没跑。

### 根因：一个布尔值要满足两个矛盾需求

- 沙箱分支需要 `verbatim = false`：`confine` 返回的 argv 里有 `C:\Program Files\...` 这类带空格路径，必须让 Node 正常转义，否则被劈成多个参数（0.2.1 修的）。
- cmd 命令段需要 `verbatim = true`：objective 里的 `"` 必须原样交给 cmd，否则 Node 按 MSVC 规则转义成 `\"`，而 `cmd.exe /c` 的余下部分**不按那套解析**。

一个布尔值满足不了两个相反的要求。报告这个判断是准的。

### 修法：命令本体走环境变量

采纳报告的方案。`confine` 之后若 argv 尾部是 `cmd.exe /d /s /c <命令文本>`，把那一段换成 `%COORD_JOB_CMD%`，真身进环境变量。这样 `verbatim` 仍然是 `false`（保护带空格路径），引号问题从根上消失。

```js
argv[argv.length - 1] = `%${JOB_CMD_ENV}%`;
jobCmdViaEnv = firstLine;
```

环境变量名**不能以 `DSH_` 开头** —— `scrubbedParentEnv()` 会把 `DSH_*` 全滤掉。报告提醒了这条，我用了 `COORD_JOB_CMD`。

### 我在这里踩了一个坑，值得记下来

第一版索引写成 `argv[argv.length - 4]` 取 `cmd.exe`。真实 `confine` 返回的是 **5 段数组**：

```
["cmd.exe", "/d", "/s", "/c", "echo \"quoted ok\""]
   len-5      len-4  len-3  len-2   len-1
```

`len-4` 取到了 `/d`，判定不成立，**修复静默失效**。

而当时源码断言是绿的 —— 因为那条只查「`COORD_JOB_CMD` 这个字符串在不在源码里」，在。**是端到端跑真 spawn（`草稿/q-e2e-quote.mjs`）才发现的**：

```
confine 收到的 argv: ["cmd.exe","/d","/s","/c","echo \"quoted ok\""]
实际输出: "\\\"quoted ok\\\""
❌ 失败：引号仍被转义 —— 修复没生效
```

改对下标后：

```
实际输出: "\"quoted ok\""
✅ 通过：引号完好
```

所以测试里现在有两条：33.1 端到端真跑，33.2 直接断言下标是 `length-5`。**只查字符串存在是假绿**，这一课又交了一次学费。

## Bug 2：job 被取消后落 `failed` 而不是 `cancelled`

### 报告说的

```
[task.cancel_requested] ...（native: jobs.kill (requested)）
[task.failed] exit 1                     ← 期望 task.cancelled
```

### 我实测了「为什么是 exit 1」

`草稿/q-jobkill.mjs`：真起一个 `ping -n 30`，3 秒后 `taskkill /T /F`：

```
close 在 10541 ms 后触发
  code   = 1   (类型 number)
  signal = null
```

**`taskkill` 杀掉 cmd.exe 时给的是 `code=1`、`signal=null`，不是 `killed`。** 所以插件的 producer 报：

```js
resolve(code === 0 ? { status: 'completed' } : { status: 'failed', detail: `exit ${code}` });
// → { status: 'failed', detail: 'exit 1' }
```

宿主 `jobs` 原样采纳这个 outcome（`dsh-jobs-local:771` `job.status = outcome.status`），`settled` 事件里就是 `failed`。

### 报告定位到 settled 处理器，但那只是下游

报告给的补丁是在 `settled` 映射里加一行 `t.status === 'cancel_requested' ? 'cancelled' : ...`。那行**是对的、必须加**，但它是在**下游补救**。

我做了两层：

**第一层（源头）**：producer 自己知道「本进程下发过 cancel」。`cancel()` 里先标记，`close` 处理器读到标记就报 `killed`（宿主 `JobStatus` 的原生枚举里有这个词）：

```js
const how = signal ? `killed by ${signal}` : `exit ${code}`;
if (cancelRequested) { resolve({ status: 'killed', detail: how }); return; }
```

退出码照样写进 `detail`，**事实没丢**，只是状态归「取消」。

**第二层（下游）**：照抄报告那句，与 subagent 侧的 A07 会合规则对齐：

```js
t.status === 'cancel_requested' ? 'cancelled' :
st === 'completed' ? 'succeeded' : ...
```

为什么两层都要：宿主版本不同、或 `kill` 的原生实现变化时，仍可能只给 `failed`。源头给正确事实，下游兜一次底，任何一边失效都还能收敛。

## 另外两条（不是 bug，采纳进 README）

### 测试要在无沙箱终端跑

报告说在 DSH 自己的 `workspace-write` 会话里跑 `regression.mjs`，A1 会因 `spawn EPERM`（受限 token 下 `windowsHide` 的 CREATE_NO_WINDOW 被拒）假失败。

**这条我这边复现不了**：我这个会话的文件策略是 `danger-full-access`，A1 直接通过：

```
✅ A1 建 job 成功  (已受理后台任务：build)
```

所以我不是「验证了它对」，是「我这边的环境撞不到」。但它描述的现象有具体成因（受限 token + CREATE_NO_WINDOW），且报告作者在他那台机器上撞到了。**按建议写进 README，并注明未在本机复现。**

### 旧台账不迁移

0.1.x–0.2.3 的 `<homedir>/.dsh/background-task-coordinator/tasks.db` 不会被新版读（新版读 `<profile>/tasks.db` 或 `<profile>-<hash>/tasks.db`）。历史会「突然空了」，但不报错。

本机实测确实如此：台账在 `.../background-task-coordinator/desktop/tasks.db`，无指纹（标准 home）；报那台 `DSH_HOME=D:\.dsh`，于是是 `desktop-4f58238f/tasks.db`。指纹机制在 `index.js:56-96`。

要不要加「旧根 tasks.db 存在且新目录为空 → 一次性 move」：**这版没做**。自动搬动别人的数据文件风险大于收益，而且「空着不报错」比「搬错」好收拾。写进 README 让用户自己决定。
