## 一、补丁 C：订阅 `agent/disposed`

### 为什么需要

`index.js` 顶部注释从 0.1.x 起就写着四个事件：

```
'subagent/start' / 'subagent/end'
'agent/status'({ agent, status }) / 'agent/disposed'({ agent })
```

但代码只实现了 `subagent/end` 一个。**注释许诺了四个，实现了一个** —— 典型「看着像做了」。

后果：子代理被外部销毁（父会话关闭、归档、`drain`、宿主清理）时收不到 `subagent/end`，台账一直 `running` 占配额，只能等用户手动调两次 `task_list` 靠 miss 计数落 `lost`。

### 实现

```js
const offDisposed = ctx.on('agent/disposed', (payload) => {
  const sid = payload?.agent?.id;
  if (!sid) return;
  const t = d.findActiveByNative(String(sid), [...ACTIVE], 'subagent');
  if (!t) return;                                   // 不是本插件管的，安静走开
  const wasCancel = t.status === 'cancel_requested';
  const terminal = wasCancel ? 'cancelled' : 'lost';
  // ... 写台账 + emitEvent + settleNotification(selfProduced: true)
});
```

`cancel_requested` → `cancelled`（协调器请求过，销毁即确认）；其余 → `lost`（外部销毁、没收到 `subagent/end`）。

### 一个必须先回答的问题：插件级 `ctx.on` 收得到吗？

契约写着 `Scope-filtered dispatch`。如果插件顶层的 `ctx.on` 收不到子代理 scope 的事件，这个订阅就是个**永远不触发的空订阅**。

去查 `dsh-scope:327-338` 的过滤实现：

```js
function scopeTarget(base, key) {
  const baseFilter = base[ctx.filter];
  const carrier = { [Context.filter](ctx) {
    if (baseFilter !== void 0 && !baseFilter.call(base, ctx)) return false;
    const tag = scopeOf(ctx);
    if (tag === void 0) return true;                          // ← 未打标记的监听器全局放行
    for (let cursor = key; cursor !== void 0; cursor = scopeParents.get(cursor)) if (cursor === tag) return true;
    return false;
  } };
```

`332` 行 `if (tag === void 0) return true;` —— **未打 scope 标记的监听器全局放行**，插件顶层 `ctx.on` 正属于这一类。

**而且本机有实证**：`task-mwwaq4jb-n5yv` 的终态事件 note 是 `completed`，那是 `subagent/end` 的 `stopReason` 原文 —— 证明插件级 `ctx.on('subagent/end')` 真能跨 scope 收到。`agent/disposed` 走同一套 carrier（`subagent:2994` `scopeTarget(this, parent)`），机制一致。

第 34.1–34.5 条测试把这个订阅钉住了：不是空订阅、running→lost、cancel_requested→cancelled、未知 agent 不误伤、终态不重复写。

### 边界（写进 README）

- **只覆盖 subagent，不覆盖 job**（job 没有 agent 生命周期）
- 从没解析出 `nativeSessionId` 的任务匹配不上，仍靠 sweep 兜底
- **所以它是改善，不是探活的替代**

## 二、补丁 D：超时清账补真取消

### 为什么需要

`index.js` 的超时分支对活着的 subagent 只做探活：

```js
if (t.type === 'subagent' && t.nativeSessionId) {
  let gone = false;
  try { gone = !getAgentHandle(ctx, t); } catch { gone = false; }
  if (gone) { /* 落 lost */ }
}
```

`gone === false`（原生还活着）时**什么都不做**，只等一个可能永远不来的 `subagent/end`，任务就卡在 `cancel_requested`（issue #1 A4 的真形态）。

### 为什么必须 `keepInbox: false`

这是整条链能不能跑通的分界，`草稿/q-poke-chain.mjs` 六环验证：

```
1. cancel() → inbox.clear()                              ← agent-loop:93-96
2. clear() → splice() → mutate(..., discardRemoved=true) ← agent-loop:159-161
3. mutate() → emit 'agent/inbox/discarded'               ← agent-loop:205
4. subagent 订阅了 agent/inbox/discarded                 ← subagent:1862
5. handler = wakeSettlement → this.wake(activation)      ← subagent:1855-1857
6. wake() → activation.poke.resolve()                    ← subagent:1917
   → settlementState 被重算 → 判 ready → 发 subagent/end
```

**第 4 环是关键**：`subagent:1860-1862` 订阅了收件箱的三个事件（`inserted` / `claimed` / `discarded`），每次都唤醒结算观察者。清空收件箱本身就是一个 `discarded` 事件，正好触发它。

用 `keepInbox: true`（`interruptByParent` 走的就是这条）就退回「等 poke」的死等。

### 实现

```js
if (typeof handle?.cancel === 'function') {
  handle.cancel({ kind: 'user' }, { keepInbox: false });
  // 落 cancel_requested，摘要写明丢弃了几条未投递指令
  continue;    // ← 必须有这个 continue
}
```

### 「丢弃 N 条」那个 `continue` 是实测踩出来的

第一版写完 `errorSummary` 就结束了，**没有 `continue`**。结果掉进后面的通用分支：

```js
if (t.status !== 'cancel_requested') {
  d.updateTaskFields(t.id, {
    status: 'cancel_requested',
    errorSummary: `已超 deadline（...），已请求取消，等执行器确认`,   // ← 覆盖掉上面写好的
  });
}
```

实测输出：

```
ag.cancel 被调用: true
  cause={"kind":"user"}  opts={"keepInbox":false}
台账 status: cancel_requested
errorSummary: 已超 deadline（1 分钟），已请求取消，等执行器确认     ← 我给的那句被吃了
```

加上 `continue` 之后：

```
errorSummary: 已超 deadline（1 分钟），已下发真取消（keepInbox=false）
```

**这是「改对了但被后面覆盖」的典型**——和 0.1.4 那次 `wrapped` 算了不用是同一类：代码写了，没生效。测试 34.9 就是这个 `continue` 的固化。

### 关于「丢弃 N 条」的一个实测说明

`listPendingMessages` 查的是 `status='pending'` 的消息。但实测发现（`草稿/q-chk-pending.mjs`）：

```
绑定前: [{"status":"pending","n":2}]
绑定后: [{"status":"delivered","n":2}]     ← 绑定成功就全投出去了
```

**`task_register_delegation` 一成功就把 pending 全投出去**，所以「超时时还有 pending」只在「绑定之后、投递失败、又排队了」这种边缘情况下出现。

我没有强行构造那个场景（要同时满足好几个条件，造出来的不是真实路径）。这条如实记在这里：**代码逻辑正确，但触发窗口很窄。**

## 三、更正我那份核查的两处错

`Downloads/result (1).md` 对我的《子代理清理核查》提了 4 条批评。逐条验完，**两条它对我错，两条它错我对，一条对一半**。我改了自己的两处，也指出它一处核心论证有问题。

### 3.1 它错：断链点 A「poke 没人捅醒」

它说 `inbox.clear()` 不会调用 `wake(activation)`，所以 `poke.promise` 没人捅。

**漏了 `subagent:1860-1862` 那三个订阅。** 上面第二节那条六环链就是反驳：清空收件箱发 `discarded` 事件，正好被订阅，正好 `wake`。

### 3.2 它对：断链点 C「已 closed 不可能再发第二个 subagent/end」

这条它对，而且**推翻了我原来的说法**。

我原来写「驻留的是收件箱空的 idle 代理，占注册表条目」——**错的**。`finishDisposal`（`subagent:1977-2041`）：

```js
await activation.handle.dispose();    // 2025：Agent 被销毁
this.resident.delete(childId);        // 2033：移出驻留表
activation.observer.settle(terminal); // 2041：发 subagent/end
```

**结算和销毁是同一个事务。** close 之后 agent 已经不在 `ctx.agents` 里，不留驻留实例。

所以「对 idle 子代理 cancel 能促发结算」只在**还没自然结算**的窗口内成立。一旦结算过，`getAgentHandle` 查不到，走 miss 计数落 `lost` —— 那条路是通的，但它叫「探活兜底」，不叫「cancel 触发结算」。

### 3.3 它对：§6.2 的实测没覆盖 idle 取消

确实没覆盖。台账那两条取消（A07b、回归②）的 `stopReason` 都是 `aborted`，说明取消时子代理**正在 running**，走 `abort` 分支，不是「idle 时清收件箱」那条。

**样本不足，承认。** 但话要说全：台账现状是 9 条 subagent、0 条卡在 `cancel_requested`。样本小到不能证明「不会卡」，也小到不能支撑它说的「最常见」。

### 3.4 它对：`whenIdle` 可以做成零阻塞探针

我在核查 §7 写「`whenIdle()` 是个 await，不是可以顺手查的状态位」就放弃了。**下结论太草率。**

它给的方案实测可行（`tests/manual/whenidle-probe.mjs`，5 个场景）：

```
✅ 1. 真空闲 → true
✅ 2. 正在跑 turn → false
✅ 3. 正在 maintenance(/compact) → false（不误杀）★
✅ 4. maintenance 结束后 → true
✅ 5. 对照：status 在 maintenance 期间报 "idle"（会误判），探针报 false
```

第 3、5 条是关键：**这就是我当时需要但说「做不到」的能力。**

**但这一版没用它**：补丁 C 已经覆盖了「被销毁」这个主要场景，补丁 D 覆盖了「超时」。这个探针是给「已 `cancel_requested` 且超过二次宽限期仍没事件」的**最终兜底**用的，属于第三层，先留着不进这版 —— 加太多次级收尾会让状态机难推理。

### 3.5 它对一半：「原地退休标记只改几个 frame」

**机制上它对**：catalog 投影只认 `event.type === 'subagent/catalog'`（`catalog.js:74`），改掉 type 就不进投影；`seq` 不动所以 `inheritedEventCount` 不受影响；不是 surface 事件，不影响模型看到的内容。

**但「其余 8440+ 帧原字节不动」做不到。** 拿真实文件实测（`tests/manual/retire-frame-test.mjs`）：

```
总 frame: 8478  文件 125.8 MB
目标 frame #1115  原长 441 字节

改为 type="subagent/retired"（等长：16 → 16 字符）
  重压后: 439 字节
  差: -2 字节          ← 等长改 type，压缩后仍然短了 2 字节
```

**改两个字符，压缩后长度就变了。** 后面所有 frame 的字节偏移要重算 —— 等于把整个文件重写一遍。这不叫「不动其余帧」，只是「逻辑上只改了 6 条事件」。

它提到的三个社区插件（`dsh-plugin-subagent-delete` / `dsh-plugin-subagent-clean` / `dsh-agent-manager`）**我无法证实存在**：本机没装，`web_search` 没有 API key 用不了。能证实的只有机制部分。

### 3.6 它对：0.3.0 方案的三个死角

1. **`interruptByParent` 分支自相矛盾** —— 我在核查 §2.3 刚证明它硬编码 `keepInbox: true` 会死等，§7 又写「补一次 `ag.cancel` 或 `subagents.interruptByParent`」。**确实矛盾。这版只写 `ag.cancel({keepInbox:false})`，不提 `interruptByParent`。**
2. **有孙代理时只取消父级不够** —— `settlementState:1972` `if (activation.ownedChildren.size > 0) return "wait";`，孙代理没结束父就永远 wait。而 `drainDescendants(parents)` 的粒度是**整个父 Agent**（`subagent:1333`），不是单个子代理，插件层没法「只清一个子代理的孙代理」。**这条仍未解决**，记进待办。
3. **`agent/disposed` 的 scope 订阅要先实测** —— 提醒得对，已按 3.1 前面那节实测确认。

## 五、新增 `tests/manual/` —— 为什么要有

这一版加了 8 个手动验证脚本，不进 `npm test`。

**直接原因**：0.2.10 我把 `argv[length-5]` 写成 `argv[length-4]`，**源码断言（查 `COORD_JOB_CMD` 在不在）是绿的** —— 是端到端跑真 spawn 才抓到的。

**只查字符串 = 假绿。** 这些脚本就是第二意见：

| 脚本 | 验什么 | 要宿主源码 |
|---|---|---|
| `verbatim-compare.mjs` | 引号退化的两种交付方式对照 | 否 |
| `e2e-quoted-cmd.mjs` | 端到端：沙箱分支下引号完好 | 否 |
| `jobkill-close-code.mjs` | taskkill 后 code=1 / signal=null | 否 |
| `e2e-timeout-cancel.mjs` | 端到端：超时真下调 cancel | 否 |
| `poke-chain.mjs` | 六环唤醒链完整 | **是** |
| `close-vs-dispose.mjs` | 结算与销毁同一事务 | **是** |
| `whenidle-probe.mjs` | whenIdle 竞态探针 5 场景 | 否 |
| `retire-frame-test.mjs` | 改 frame 后长度必变 | 真会话文件 |

用法与解压方法见 `tests/manual/README.md`。
