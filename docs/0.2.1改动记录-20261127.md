# 0.2.1 改动记录（2026-11-27）

0.2.0 发布后收到一份**带行号和复现方法**的逐行核验报告（基线是 0.1.7 那份深度分析的 19 项隐患）。它的核心结论是：

> 作者确实非常认真地推进了四轮迭代，解决了约 70%–75% 的实质风险，但多项修复存在盲区或半成品状态，**且在修补过程中新引入了 6 个可复现的退化/Bug**。

我把每一条都对着代码核了一遍。**结论：这份报告基本是对的，七处退化全部属实，且都是我在 0.1.8–0.2.0 这三轮里自己引进来的。**

这一版逐条修掉。

---

## 一、越权：`task_register_delegation` 漏了 `ownedBy`（P0-3）

### 这条最严重

0.2.0 给六个工具补了归属校验，唯独漏了 `task_register_delegation`。

后果不是「少一道检查」那么简单：

```
1. 攻击者会话知道受害者的 taskId
2. 调 task_register_delegation，把受害者的任务绑到自己的子代理上
3. 0.2.0 新加的 pending 补投立刻执行
   → 受害者排队中的指令原样投进攻击者的 agent
```

**0.2.0 新加的「pending 补投」把这个洞从「能看」升级成了「能偷」。** 报告用的复现载荷是 `SECRET_TOKEN=xyz123`。

修法：补 `ownedBy(row, exec)`，与其他六个工具一致。

验证：攻击者登记被拒；受害者的 pending 没被投给攻击者；任务 owner 未变。

## 二、冒充 owner 读别人的输出（P0-3 第二处）

`task_describe` 里读 job 输出时：

```js
// 0.2.0
const caller = rowFull?.ownerSessionId ?? undefined;   // 「谁创建的」，不是「谁在调」
ctx.jobs.get(t.nativeId, caller);
ctx.jobs.readAt(t.nativeId, 0, caller);
```

这等于替别人的任务冒充 owner 去读输出，把 DSH 0.2.2 特意加的 `assertAccess` 围栏直接穿透了。

修法：改成 `own.caller ?? own.owner`。上面已经过了 `ownedBy`，所以 caller 要么是真的调用者，要么拿不到身份（历史兼容）。

**有一处我保留了用 owner 作 caller**：启动对账。它跑在 `apply()` 里，没有「当前调用者」这回事，做的事是替每个任务各自核实自己的原生状态（一对一，不是借身份去看别人的东西）。这是允许的，代码里写明了区别。

## 三、`task_cancel` 分支顺序错，未绑定的 queued 子代理被锁死（P0-2 残缺）

```js
if (ag && …)                          // 有 handle
else if (ag)                          // 有 handle 但没 cancel
else if (!hasRealId)                  // ← 3 抢在 4 前面
  nativeOk = '未解析出会话 id，未探活…'
else                                  // 「根本没绑上」永远进不来
  落 cancelled
```

对一个**从未调用过 `task_register_delegation`** 的 queued 子代理点取消，不会落 `cancelled`，而是陷入 `cancel_requested` 等一个永远不会到来的 `subagent/end`。

修法：把「从未绑定」（连 agent 名都没有）单独拆出来，直接落 `cancelled` —— 它从来没跑起来过，事实清楚。有 agent 名但反查不出 id 的「已绑定」任务才走 `cancel_requested`。

## 四、`getAgentHandle` 抛错后三处没接（审计 #1）

0.1.10 把 `getAgentHandle` 内部的 try/catch 去掉了，目的是让调用方能区分「查不到」和「查询失败」。但三处调用点没跟着改：

| 位置 | 后果 |
|---|---|
| `sweepOnce` | 一条子代理查询瞬时异常 → **打崩整个 `task_list`** |
| `task_append_message` | 直接崩工具，而且崩在「已删除旧 pending 行」之后 → **消息凭空消失** |
| 启动对账 | `catch { alive = false }` 把异常当「已死」，误判 `lost` |

修法：

- `sweepOnce`：接住，**本轮跳过**（既不算死也不算活，下轮再试）
- `task_append_message`：接住，状态留 `pending` 而不是 `undeliverable` —— 探活失败 ≠ agent 不在，不能把一条可能投得出去的消息判死
- 启动对账：保持 `catch { alive = false }` 但注释说明这是「重启后无法重连」的语义，与工具路径不同

**顺带修了一个更隐蔽的问题**：0.2.0 是「进门就删掉旧 pending 行」，然后才探活。探活一抛，旧记录没了、新的也没写进去。现在把删除封成 `mustPurge()`，只在**确定要写新行之前**调用。

## 五、迁移剥离了外键与 CHECK（审计 #3）

`migrateMessagesUnique` 里建新表时：

```sql
CREATE TABLE task_messages_v2 (
  task_id TEXT NOT NULL,          -- ← 少了 REFERENCES tasks(id)
  status  TEXT NOT NULL,          -- ← 少了 CHECK (status IN (...))
  ...
```

重建后的表**比迁移前更松**，而且它无条件运行（连全新建库都会因 meta 无版本号触发重建）。实测可直接插入指向不存在任务的孤儿消息和 `status = 'TOTALLY_BOGUS_STATUS'`。

这是静默的数据完整性退化：`ACTIVE`/`TERMINAL` 判定全靠约定，一个手误的 `'runing'` 会让任务永远既不算活动也不算终态。

修法两层：

1. 新表**原样保留** `REFERENCES` 和 `CHECK`，只松开 `idempotency_key` 的列级 UNIQUE
2. 判据从「版本号够不够」改成「**表结构对不对**」—— 因为 0.2.0 已经把那个残缺表标成了版本 2，光看版本号会永远跳过修复。现在读 `sqlite_master` 的实际 DDL 判断三件事（有没有列级 UNIQUE / 有没有外键 / 有没有 CHECK），目标版本提到 3，迁移后再核一次，不对就不写版本号让下次重试

验证：孤儿消息插不进去 ✅、非法 status 插不进去 ✅、老数据全保留 ✅。

## 六、`windowsVerbatimArguments` 无条件开（审计 #6）

0.2.0 为了修「引号路径被拼坏」，给 spawn 加了 `windowsVerbatimArguments: true`。但那是**全局**的：

```js
windowsVerbatimArguments: process.platform === 'win32',   // 0.2.0
```

`sandbox.confine()` 返回的 argv 里常有 `C:\Program Files\...` 这种带空格的绝对路径。跳过 Node 的转义 → 被劈成多个错误参数。

修法：按 argv 的**来源**决定。

```js
if (policy.mode === 'danger-full-access') {
  argv = wrapped;  verbatim = true;    // 我们自己拼的 cmd /d /s /c，后面那段要原样交
} else {
  argv = sandboxed.argv.map(String);  verbatim = false;   // 包装器路径必须正常转义
}
…
windowsVerbatimArguments: process.platform === 'win32' && verbatim,
```

验证：两条分支各自跑一遍带空格路径的命令，都能出正确结果。

## 七、`resolveSubagentSessionId` 漏 `caller.id` + 盲信 `given`（P1-6，报告标「完全未修」）

两处：

**① 父会话 id 的取法不全**

```js
const parentSid = caller?.session?.id ?? caller?.sessionId ?? null;   // 0.2.0
```

漏了 `caller.id`。而 `task_register_delegation` 里的空态兜底恰好造的是 `{ session: { id }, id }` 形态，别的宿主也可能只给 `.id`。结果 `{ id: 'parent-only-id' }` 这种 caller 会让 `listChildren` 路径整个跳过、直接返回 `null`。

**② `given` 盲信**

```js
if (g && g !== name) return g;   // 0.2.0：给了就信，直接落库
```

这个字段由模型填，什么都能塞进去。随手写的字符串会被当成会话 id 存进 `native_session_id`，之后所有按 id 的探活、结算匹配、取消全部落空。

修法：补 `caller.id`；`given` 先做「像不像 id」判断。

**这里有个取舍要说清楚。** 报告建议严格校验，我第一版写成「必须是 UUID」，结果把 `sess-F1` 这种合法短 id 也打断了 —— 补投直接失效，测试立刻报红。这说明**过严的校验会打断正常时序**（原生工具刚返回 sessionId 时，agents 注册表往往还没登记）。

最终判据：只排除明显是话不是 id 的（空、含空格、纯中文、长度 < 4），其余接受；注册表能查到就是「已确认」，查不到算「未核实」但照样用。

## 八、`config` 对 `task_create` 不生效（审计 #4）

`apply(ctx, config)` 收了 config，`LIMITS_READ()` 也读了它 —— 但 `task_create` 里另写了一套只读环境变量的 `LIMITS`，两套各算各的：

```
传 { global: 1 } → 仍然能建第 2 个任务
传 { timeoutMinutes: 5 } → deadlineMinutes 仍落 120
```

修法：删掉 task_create 里那套，统一走 `LIMITS_READ()`（内置默认 → yml config → 环境变量），`LIMITS_READ` 补上 `global`/`perOwner` 两项，并用函数形式提到 `apply` 开头（否则是暂时性死区 —— 这个我改的时候撞了一次，`Identifier already declared` 报了才想起来）。

验证：config 写 `{global:1}` 时第二个被挡、`{timeoutMinutes:5}` 时 `deadlineMinutes` 真的落 5。
