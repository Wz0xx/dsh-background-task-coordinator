## 一、LIMIT 500 全表截断（审计 P1-4）——最要紧的一条

### 原来错在哪

八处核心查询都是 `listTasks({ limit: 500 })` 拉前 500 条再内存过滤：

| 位置 | 用途 | 后果 |
|---|---|---|
| `sweepOnce` | 探活兜底 | 活动任务掉出窗口 → 永远扫不到 |
| 限额检查 | global/perOwner | 不计限额，能无限建 |
| `task_list` | 列任务 | 在跑的任务看不见 |
| 启动对账 | 重启后修正 | 漏掉的不修正 |
| `subagent/end` | 结算 | **事件到了匹配不上，永久丢** |
| `jobs.settled` | 结算 | 同上 |
| 维护循环 | 超时清账 | 永不超时 |
| `loadTasks` | 旧投影入口 | 同上 |

而且 `listTasks` 的 `ORDER BY priority ASC, created_at DESC` 让优先级数字小的历史任务**永远排在前面**，活跃任务被挤出去更快。

### 改法

新增/启用三个定向查询，全都走索引：

```js
findActiveByNative(nativeId, activeStatuses, type)  // 走 idx_tasks_native_session
listActive(activeStatuses)                          // 走 idx_tasks_status
listRecent(limit, ownerSessionId)                   // 按 created_at 倒序取窗口
```

`subagent/end` 与 `jobs.settled` 改成：

```js
const t = d.findActiveByNative(sid, [...ACTIVE], 'subagent');
```

顺带解决了第二个毛病：旧写法命中**已终态的历史记录**就 `return`，漏掉真正活跃的那条。

### 补的索引

```sql
CREATE INDEX idx_tasks_native_session ON tasks(native_session_id);   -- 之前缺失
CREATE INDEX idx_tasks_status_created ON tasks(status, created_at);
```

### 验证

造 601 条台账（600 条终态历史 + 1 条在跑）：

- `findActiveByNative` 命中 → ✅
- 旧 `listTasks({limit:500})` 确实漏 → ✅（**这条专门用来证明 bug 真实存在过**）
- 601 条时 `subagent/end` 仍落账 → ✅

## 二、`purgeHistoryOlderThan` 定义了从没调用

实现完好，只是没人调。台账与幂等表只增不减，跑到 500 条之后上面那串毛病就开始了。

现在接进维护循环，并且**幂等表一起清**（以前只删任务行，`idempotency` 表的通知账永远留着）：

```js
const days = Number(LIMITS_READ().retentionDays);   // 默认 30，<=0 关闭
if (days > 0) d.purgeHistoryOlderThan(now - days * 86400000);
```

清理失败只记日志，不影响同一轮的超时扫描。

## 三、幂等键是全表 UNIQUE，不是 `(task_id, key)`

### 这条的后果比看起来严重

任务 A 用 `"step-2"` 投过一条 → 任务 B 再用 `"step-2"`：

- 消息**真的投给了子代理**（`followup` 成功）
- 写库 `INSERT` 撞全表 UNIQUE，`insertMessage` 吞掉异常返回 `false`，**调用方没检查**
- 结果：agent 收到了，台账里 0 条记录。审计和幂等同时失灵。

### 改法：重建表 + meta 版本机制

SQLite 不能 ALTER 掉列级 UNIQUE，只能重建。判据是 `meta` 里的版本号：

```sql
-- meta: schema.task_messages.unique = 2
CREATE TABLE task_messages_v2 (...);            -- 无列级 UNIQUE
INSERT OR IGNORE INTO task_messages_v2 SELECT ... FROM task_messages;
DROP TABLE task_messages;
ALTER TABLE task_messages_v2 RENAME TO task_messages;
CREATE UNIQUE INDEX uq_messages_task_key ON task_messages(task_id, idempotency_key);
```

整个迁移包在 `BEGIN IMMEDIATE` 里，失败回滚并抛给调用方。老库数据一条不丢（联合唯一比全表唯一宽松，不可能冲突）。

### 验证（做了两层）

第一层，用本机**真实旧库**（0.1.x 状态下由全表 UNIQUE 建出来的那份，含 2.1 MB WAL）跑迁移：

```
迁移前：task_messages 有 idempotency_key TEXT NOT NULL UNIQUE
迁移后：29 条任务 / 53 条事件 / 5 条消息全在
        sqlite_autoindex_task_messages_1, idx_messages_task, uq_messages_task_key
        meta.schema.task_messages.unique = 2
真实库上跨任务插入同一 key → A=true B=true，两条都在
```

第二层，测试里造一份老 DDL 库，验证：约束松开 ✅、联合索引建上 ✅、老数据不丢 ✅、跨任务可复用 ✅、同任务同 key 仍唯一 ✅、重复打开不重复迁移 ✅。

## 四、`pending` 消息不 flush（审计 P1-5 ①）

### 原来的死结

`task_append_message` 在没绑定时落一条 `pending` 并承诺「绑定后补投」，但 `task_register_delegation` **根本没有 flush 逻辑**。而且内容哈希幂等键让重发同样的指令被「已是 pending，未重复投递」挡回去 —— 消息永久卡死。

### 两处都改了

**绑定后补投**：`task_register_delegation` 成功绑定后，把 `listPendingMessages(tid)` 逐条投出去，成功标 `delivered`，失败标 `undeliverable` 并写原因。拿不到 agent 句柄的**保持 pending**（不假装投出去了，也不判死）。

**幂等判据改成按状态**：

```js
// 旧：命中就挡（包括 pending / undeliverable）→ 永久锁死重试
// 新：只有 delivered / cancelled 才挡
const settled = prior.find(m => m.status === 'delivered' || m.status === 'cancelled');
```

没成的那条在重投前**删掉**（不是改成 cancelled —— 同一 key 只允许一行，留着旧的照样撞索引，那正是第三条 bug 的形态）。那些行从没投成功过，删掉不丢事实；投递尝试本身已经写在 `task_events` 里。

### 顺带堵住终态复活

`task_register_delegation` 以前不校验终态，对已 `succeeded` 的任务再调一次会把它改回 `running`，还留着旧 `completed_at`。现在直接拒绝。

## 五、GBK 三重乱码（审计 P2-6）

### 原来错在哪

```js
// 0.1.x：首个 chunk 试解一次就永久锁定
try { new TextDecoder('utf-8',{fatal:true}).decode(buf); enc='utf8'; }
catch { enc='gbk'; }
```

Windows 命令的第一个 chunk 常常是**纯 ASCII**（`echo` 之前什么都没打），UTF-8 严格解码当然通过 → 锁成 `utf8` → 之后所有 GBK 中文全乱码。三重问题：锁定过早、没有 `{stream:true}`（多字节字符跨 chunk 被劈开）、没有 `end()` 收尾（最后一行缺字）。

### 改法

```js
// 纯 ASCII 直接吐（两种编码下字节一致），但不锁定
// 首次出现非 ASCII 才判：整段缓冲严格试 UTF-8，通过=utf8，不通过=gbk
// 判定后用单一持久 TextDecoder + {stream:true}
// decoder.end() 在 close 时冲干净尾巴
```

判定时若严格解码失败，会**掐掉尾巴 1~3 字节再试**，用来区分「这不是 UTF-8」和「UTF-8 字符正好跨在 chunk 边界」。

### 验证

用可控脚本精确构造：先吐 `ABC\n`（这步以前会锁死编码），再吐 GBK 的 `D6`，**260ms 后**再吐 `D0 CE C4 0A` —— 故意把「中」的两个字节劈在两个 chunk 里。

```
输出："ABC\n中文\n"       ← 解码正确
跨 chunk 半字没被切断     ← 无替换符、无乱码区
```

## 六、多 profile 共享单库 + `dispose()` 不关 `_sqlite`（审计 P2-7）

### 串台会真丢状态

所有 profile 写同一个 `~/.dsh/background-task-coordinator/tasks.db`。开第二个 profile 时，它的启动对账查不到第一个 profile 内存里的 job/agent，会把**正在跑的任务全部标 lost**。

### 改法

```js
function dataDir() {
  const raw = process.env.DSH_PROFILE_DIR;          // 宿主给的真值，优先
  const tag = raw ? basename(raw) : (DSH_PROFILE ?? DSH_PROFILE_NAME ?? 'default');
  return path.join(HOME_DATA, sanitize(tag));
}
```

现在是 `~/.dsh/background-task-coordinator/<profile>/tasks.db`。

**旧库不自动搬** —— 串台路径不清不楚，搬错比不搬更糟。要留老数据就手动 copy 到新目录（本机 `desktop` profile 对应目录已经建好，见下方「本机」一节）。

另外加了两条：

- `PRAGMA busy_timeout = 5000` —— 跨进程并发写不再直接抛 `SQLITE_BUSY`
- `dispose()` 里 `_sqlite.close()` —— 以前只摘订阅和定时器，句柄一直攥着：插件重载会累积连接、`-wal` 永不 checkpoint、Windows 上库文件还被锁住删不掉

`close()` 里先 `PRAGMA wal_checkpoint(TRUNCATE)` 再关。

### 验证

两个 profile 各自开一次 → 两份库落在两个目录、不是同一个文件；`dispose()` 之后库文件能删掉（Windows 上句柄没释放是删不掉的）。

## 七、`stopReason` 空串落 failed（审计 P2-2 的残留）

### 先说清楚上一版错在哪

0.1.7 把白名单改成 `completed|end_turn|stop|stop_sequence|success|succeeded|done`，其余一律 `failed`。听着严谨，但**宿主实际不发这些词**。

本机 0.2.1-rc.4 的 asar 里 `SubagentStopReasonMap` 原文：

```ts
{ completed: 'completed', aborted: 'aborted', error: 'error',
  'max-tokens': 'max-tokens', refusal: 'refusal' }
```

于是 `completed` 能过，但**空 `stopReason` 会被判成 failed** —— 那是编造失败，和以前编造成功一样糟。

### 改成按真实枚举映射

```js
cancelled  = cancel_requested || /^(aborted|cancel|canceled|cancelled)$/i
failed     = /^(error|max-tokens|max_tokens|max-turns|max_turns|timeout|refusal|budget_exceeded|context_length)$/i
succeeded  = 其余
```

空串 / 未知词落 `succeeded`，但 `resultSummary` 明写：

```
子代理已结束（原生 subagent/end；stopReason=未给出，非失败词）
```

**让读的人知道这条结算的依据是「事件到了且没有报错」，不是「确认成功」。**

### 验证

| stopReason | 期望 | 结果 |
|---|---|---|
| `completed` | succeeded | ✅ |
| `''`（空） | succeeded + 注明未给出 | ✅ |
| `max-tokens` | failed | ✅ |
| `refusal` | failed | ✅ |
| `error` | failed | ✅ |
| `aborted` | cancelled | ✅ |

## 八、顺手修掉的真 bug：引号路径被拼坏

这是做 GBK 测试时撞出来的，不属于原七条，但比其中几条更容易把人坑住。

### 现象

objective 写 `node "C:\某目录\脚本.js"`，实际报：

```
Error: Cannot find module 'C:\...\"C:\某目录\脚本.js"'
```

### 原因

插件用 `cmd.exe /d /s /c <objective>` 执行。Node 的 `spawn` 默认按 CreateProcess 规则给每个参数加引号、转义内部引号，而 `cmd /s` 又会剥一层 —— 两头一夹，引号变成字面量。**任何带引号、带空格的命令都会中招。**

### 改法

```js
spawn(argv[0], argv.slice(1), {
  ...,
  windowsVerbatimArguments: process.platform === 'win32',
});
```

不再转义，argv 原样进命令行。

### 验证

`node "<path with spaces>/emit2.cjs"` → 正常输出 `QUOTED-OK`。这条已固化成测试 4.3。

## 已知坑（写进文档，省得下次重踩）

1. **objective 里的路径别加引号也能工作** —— 0.2.0 起带引号也行了，但如果你在别的 DSH 版本上遇到 `Cannot find module` 里带引号，那就是这一条。
2. **`/tmp` 在 Node 里是 `C:\tmp`** —— git-bash 的 `/tmp` 和 Node 看到的不是一回事。拷库验证时必须写 `C:/...` 绝对路径。
3. **拷 SQLite 库要连 `-wal`/`-shm` 一起拷** —— 只拷 `tasks.db`（4096 字节）会读到空库，真实数据在 2.1 MB 的 `-wal` 里。我第一次就踩了这个，差点把「空库」当迁移成功的证据。
4. **旧库不自动迁移到新 profile 目录** —— 见第六节。本机 `desktop` 目录已建好，老库还在旧位置，要留数据得手动 copy。
