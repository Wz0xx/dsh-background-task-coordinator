# 0.2.4 改动记录（2026-11-28）

这一版的起因不是代码 review，是**装上去之后发现它没在按预期工作**。

## 现场

重启 DSH 后，日志里这两行并排出现：

```
[task-coordinator] 已注册 8 个工具；数据目录 ...\background-task-coordinator\default
[task-coordinator] compat: {"overallStatus":"incompatible","missingRequired":["working_directory"], ...}
```

两个问号：

1. profile 是 `desktop`，为什么台账落到 `default`？
2. `working_directory` 为什么报不支持——宿主明明有这个服务，工具列表里甚至有 `working_directory` 工具？

---

## 一、台账目录：0.2.0–0.2.3 一直落在 `default/`

### 排查过程

先确认代码本身对不对：

```bash
$ node -e "…dataDir()…"
DSH_PROFILE_DIR = "C:\Users\stop\.dsh\profiles\desktop"
DSH_PROFILE     = "desktop"
dataDir()       = C:\Users\stop\.dsh\background-task-coordinator\desktop   ← 对
```

再确认宿主进程的环境变量：

```powershell
$ (Get-Process -Id 48784).StartInfo.EnvironmentVariables
DSH_PROFILE_DIR  C:\Users\stop\.dsh\profiles\desktop
DSH_PROFILE      desktop                                              ← 也对
```

两边都对，但插件报的还是 `default`。**所以差异一定在「插件进程看到的环境」上**：宿主主进程有这两个变量，但没传给插件所在的 host 子进程。

### 交叉验证

`default/` 那个库的 meta 是 `schema.task_messages.unique = 2`，且 task_messages **没有外键和 CHECK** —— 那是 0.2.0 代码的产物。而 `desktop/` 那个库是我 22:11 手动建的，里面才有 29 条真数据。

也就是说：**插件一直在写 `default/`，真人数据在 `desktop/`，两边从来没碰上。**

### 改法：config 是第一来源

```js
function dataDir(configHint) {
  // 真值顺序：
  //   ① config.profile / config.profileName（apply 第二参，宿主传不传我们控制不了，但至少要认）
  //   ② process.env.DSH_PROFILE_DIR
  //   ③ process.env.DSH_PROFILE / DSH_PROFILE_NAME
  //   ④ 都没有（node tests/... 直接跑）→ default
  const fromConfig = String((configHint?.profile ?? configHint?.profileName) ?? '').trim();
  ...
}
```

配套：

- `_profileHint` 模块级变量，`apply(config)` 时写入，`db()` / `dataDir()` 都用它
- `cordis.patch.yml` 里显式写 `profile: desktop`
- 启动时打一行带来源的日志：

```
[task-coordinator] 台账目录：...\desktop（来源：config.profile）
```

**这一行是为了下次能一眼看出问题**，不用再一次次去猜环境变量。

### 代价

换 profile 或改 profile 名时，`cordis.patch.yml` 里那一行得跟着改。这是个手工同步点，但比「静默落到 default」好——写在配置里，至少看得见。

## 二、`working_directory: unsupported`：查不出原因的告警

宿主服务表里 `workingDirectory` 是存在的，方法齐全（`defaultDirectory` / `get` / `ensure` / `set`）。工具列表里也有 `working_directory` 工具。那自检为什么报不支持？

原来 `has()` 长这样：

```js
const has = (fn) => {
  try { return fn() ? 'supported' : 'unsupported'; }
  catch { return 'unsupported'; }        // ← 异常被吞掉了
};
```

**「服务不存在」和「查询本身抛错」被压成同一个结果**，而且错误信息完全丢失。这和我 0.2.1 修的那三处崩溃点是同一类错误：把「没问成」当成「东西不在」。

改成记下错误：

```js
const capErrors = {};
const has = (fn, name) => {
  try { return fn() ? 'supported' : 'unsupported'; }
  catch (e) {
    if (name) capErrors[name] = String(e?.message ?? e).slice(0, 120);
    return 'unsupported';
  }
};
```

报 unsupported 时，`compat` 日志里会多一个 `capErrors` 字段，写明是哪一步抛的。

**这一条我没能当场修好**——因为要看到新的 `capErrors` 输出，得再重启一次。但至少下次它报不支持时，能告诉我为什么。

## 三、顺带验证：v2 库能不能迁到 v3

`desktop/tasks.db` 是 v2（缺外键和 CHECK），新代码打开时会走迁移。在副本上验过：

```
迁移前：版本 v2 | 外键 false | CHECK false
迁移后：版本 v3 | 外键 true  | CHECK true | 列UNIQUE false
数据: 29 任务 / 53 事件 / 5 消息 / 10 幂等账 —— 全保留
孤儿消息被拦: true | 非法 status 被拦: true
```

迁移是对的。也就是说重启后那 29 条数据会正常带过来，只是要等下一次重启才真正切到 `desktop/`。

## 五、还欠一次重启才能确认的事

写完这版代码，我得承认：**`working_directory` 那条我没修好，只是让它下次能说清楚原因。**

下次重启后看这两行：

```
台账目录：...\desktop（来源：config.profile）      ← 第一条应该对了
compat: {..., "capErrors": {...}}                 ← 第二个要看它说什么
```

`capErrors` 里如果写的是 `cannot get property "workingDirectory" without inject` 之类，那就是 cordis 服务可见性问题；如果是别的，按错误走。

**在那之前，`overallStatus` 会一直是 `incompatible`**，含义是「job 类型可能建不起来」。所以这一版不是「修完了」，是「修好了能查」。
