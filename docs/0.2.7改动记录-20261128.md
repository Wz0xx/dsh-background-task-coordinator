## 一、`working_directory: unsupported` —— 找到根因了

这条从 0.1.9 挂到现在，我一度判断「服务在插件进程里确实取不到，只能报 unsupported」。
**判断错了。** 这是一个真 bug，而且根因很具体。

### 证据链

三个服务**同时**报 unsupported：

```
sandbox.confine:     unsupported
sandbox.policy:      unsupported
working_directory:   unsupported
```

而 `jobs` / `agents` / `tools` 全部 supported。区别在哪？

**unsupported 的那三个恰好是本插件没有 inject 的三个。** 这不是巧合。

### 从 app.asar 里读出的原文

```js
get(name, strict = true) {
  return getTraceable(this.ctx, this._getImpl(name, strict)?.value);
}

_getImpl(name, strict = true) {
  const key = this.ctx[symbols.isolate][name];
  const impl = key && this.store[key];
  if (!impl) return;
  if (strict && impl.fiber.state !== 2) return;   // ← ACTIVE = 2
  return impl;
}
```

**`ctx.get(name)` 默认 `strict = true`，只返回 fiber 已 ACTIVE(2) 的服务。**

`workingDirectory` / `sandbox` / `sandboxPolicy` 不是本插件的 inject 依赖，
加载时序上它们的 fiber 可能还没进入 ACTIVE —— 于是 `ctx.get(name)` 返回 `undefined`，
自检把它读成「宿主没有这个服务」。

**服务一直在，是我们问的方式不对。**

### 修法

所有 `ctx.get(name)` 改成 `ctx.get(name, false)`：

```js
// 先不严格（能拿到实例就行），拿不到再退回严格查询
const viaGet = ctx.get(name, false) ?? ctx.get(name);
```

涉及四处：`svc()`（建任务时取 cwd / sandbox）、自检三项、`getSubagentsService()`、
adapter 里的 `getSvc()`。

### 验证

```
25.2 服务存在但未 ACTIVE 时，working_directory 仍报 supported     → supported ✅
25.3 sandbox.confine / policy 同样 supported                    → supported / supported ✅
25.4 overallStatus 不再是 incompatible                          → degraded ✅
25.5 建 job 时不因 strict 而落 cwdFallback                       → 建成功 ✅
```

**并且修了测试 mock。** 之前 `tests/mockctx.mjs` 的 `get` 完全忽略 `strict` 参数，
所以这个 bug 在测试里永远看不见 —— 这是它从 0.1.9 活到 0.2.6 的原因。
现在 mock 复刻真实语义（fiber 未 ACTIVE 时 strict 查询拿不到），
并加了 `notActive()` 辅助函数：

```js
export function notActive(obj) {
  return { ...obj, fiber: { state: 1 } };
}
```

**这一步比修复本身更重要**：测试环境不忠实，bug 就会一直漏。

## 二、脱敏漏了一条路径

实测发现：

```
同一个 detail 值：
  写事件流水   → "output: TOKEN=[REDACTED]"      ✅
  写任务摘要   → "output: TOKEN=sk-ant-LEAK999"  ❌
```

`emitEvent` 脱敏了，`updateTaskFields` 没脱敏。补四处：
job 探活补账、jobs settled 订阅、`applySubagentSettlement` 的 error/result summary。

**为什么这条要紧**：job 的 `detail` 是命令输出摘要，最容易带出密钥。
而且它落进 `tasks` 表会一直留着（不受事件清理影响）。

## 三、子代理绑定的共享语义

实测确认，行为是对的，但之前没人说清：

| 场景 | 行为 | 判断 |
|---|---|---|
| 同会话，两个任务绑同一个子代理 | **允许** | 合理需求（一个 agent 多个跟踪维度） |
| 跨会话，绑同一个子代理 | **拒绝** | 被归属校验先拦 |
| 追加消息 | **只投一次**，不因共享而重复 | 正确 |

固化成 26.1–26.4 四条断言。

## 四、无 subagents 枚举服务时的最低门槛

它的降级路径原本是「直接放行」，等于把判断全压给 metadata。我加了一层，但**只拦一种明确情况**：

```js
// candidateSid 与 agentName 都给了，agents 服务明确知道有这个东西、
// 而它跟传进来的名字对不上 → 那是把别人的 id 按到自己名下
if (agName && name && String(agName) !== name) → 拒绝
```

其余（查不到、服务不可用、注册表还没登记）一律放行。

**第一版我写成「agent 必须存在」，结果 8 条测试全红。** 那些测试构造的正是
「agent 还没登记」——而这在真实时序里非常常见（原生工具刚返回 sessionId 时）。
硬拒会打断正常绑定。这条教训写进注释了。

## 五、Windows 的权限收紧

`chmod 0600` 在 Windows 上是空操作。可以改用 `icacls`，但**默认关闭**：

```js
// 收紧后其他身份运行的工具（备份脚本、别的账户下的 sqlite 客户端）就读不到了。
// 这是改系统行为，不该由插件在启动时悄悄做。
```

改成可选：`config.tightenWindowsAcl: true` 才做。

两种模式都如实报告做了什么：

```
默认:   {"platform":"win32","applied":[],"skipped":"win32: 默认不收窄 ACL…"}
开启后: {"platform":"win32","applied":["db:user-only","wal:user-only","shm:user-only"]}
```

**不是假装成功**：`applied` 空就是没做，`skipped` 写明为什么。

## 六、脱敏是模式匹配，不是保险

把边界测出来，写成断言（28.1–28.4）：

**抓得住（8/8）：**

```
Bearer sk-ant-… / ghp_… / AKIA… / xoxb-… / AIza… / KEY=… / postgres://u:p@ / --token …
```

**抓不住（5/5）：**

```
MY_PRIVATE_BLOB=deadbeefcafe1234      自定义字段名 + 纯十六进制
data=QWxhZGRpbjpvcGVuIHNlc2FtZQ==     纯 base64
数据库口令是 海淀区123456                中文语境
key=aa11-bb22-cc33-dd44               短分段
password=abc123                       短密码
```

**零误伤（5/5）**：`npm run build`、`git status`、`ls -la`、`node app.js --port 3000`、`docker build -t x:1 .`

28.4 这条断言的意义是让「脱敏 ≠ 安全边界」这个事实留在测试里，
而不是只写在文档里没人看。

## 七、元数据正向确权路径

本机 `listChildren` 可用，走不到这条。用构造场景测了四条：

| 场景 | 结果 |
|---|---|
| 子代理已从 listChildren 移出，agents 带 `parentSessionId` 且对得上 | **放行** ✅ |
| 元数据说父会话是别人 | **拒绝** ✅ |
| 元数据空 + 列表空 | **fail-closed 拒绝**（保守取舍） |
| 正常路径（在列表里） | 放行 ✅ |

**第 3 条要说明**：什么都证明不了时宁可不绑。代价是这种宿主上的正常绑定会被拒，
需要靠 metadata 或台账唯一性补上。这是取舍不是疏漏。

## 九、还剩什么

- **`cancel` 的 `keepInbox`** —— 0.2.3 已改 `false`（取消不是暂停），这条不用再动
- **`sandbox.env` 之外的执行环境** —— `scrubbedParentEnv` 已过滤凭据类变量，
  但 `PATH` 这类还继承自宿主；如果要更强的隔离，得靠 `sandbox.confine` 给的 env
- **宿主契约依赖** —— `strict=false` 能拿到服务，但**不代表那个服务的功能一定完备**。
  自检报 supported 只说明「有这个对象且方法存在」，不说明「调用一定成功」。
