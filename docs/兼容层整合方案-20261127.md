## 二、证据基础（不靠猜）

以下每条都来自本机 `C:\Program Files\DSH NEXT\resources\app.asar` 的实际字符串/契约提取，或反馈人给出的可复核位置。

### 2.1 `subagent/end` 的真实载荷（0.2.1-rc.4）

`@deepseek-ai/dsh-subagent/types` 公开契约原文：

```ts
export interface SubagentRunEndInfo {
    readonly runId: SubagentRunId;
    readonly provider: string;
    readonly id: SessionId;          // ← 唯一的会话标识
    readonly local: boolean;
    readonly stopReason: SubagentResult['stopReason'];
    readonly lastAssistantMessage?: readonly ContentBlock[];
}

export interface SubagentRunInfo {
    readonly runId: SubagentRunId;
    readonly provider: string;
    readonly id: SessionId;
    readonly local: boolean;
}
```

**结论**：事件里没有 `sessionId`、没有 `agentId`、没有 `childId`。只有 `id`，类型 `SessionId`（子会话 id）。

反馈人说「只带一个 `id`，值是 childId（UUID）」——**对**。

### 2.2 现有代码取 id 的写法其实是对的

`index.js:1065`：
```js
const id = info?.sessionId ?? info?.childId ?? info?.agentId ?? info?.id;
```
前三个永远 `undefined`，最后兜到 `info.id`。**这一步没坏**。

### 2.3 真正坏在匹配

`index.js:1068`：
```js
.find((x) => x.nativeId === String(id))
```
只比 `nativeId`（存的是 agent 名字），没比 `nativeSessionId`。事件到了、id 也对，认不出来 → `if (!t) return;` 静默返回 → 台账永远 `running`。

### 2.4 `subagents` 服务在 0.2.1 已存在

`app.asar` 中（`@deepseek-ai/dsh-team`）：
```js
export class TeamService extends Service {
    static inject = ['agents', 'sessions', 'sessionPersistence', 'sessionProjections', 'subagents'];
```
以及 `@deepseek-ai/dsh-subagent` 的 `TYPERT_REMOTE.methods['subagents/interruptByParent'].service = 'subagents'`。

**结论**：`subagents` 是 0.2.1 就注册的 Cordis 服务键。插件可直接 `ctx.subagents` 或 `ctx.get('subagents')` 取到它——降级路径在旧版成立。

### 2.5 0.2.1 的 `SubagentRuntime` 方法面（本机实测）

```ts
listChildren(parentSessionId: SessionId, signal?: AbortSignal): Promise<SubagentCatalogEntry[]>
listDescendants(rootSessionId: SessionId, signal?): Promise<SubagentDescendantListEntry[]>
interruptByParent(childSessionId: SessionId, parentSessionId: SessionId, mode: 'continuable')
```

```ts
export type SubagentCatalogEntry = {
  readonly id: SessionId;
  readonly createdAt: number;
} & ({ readonly mode: 'one-shot'; readonly label?: string }
   | { readonly mode: 'external'; readonly label?: string }
   | { readonly mode: 'continuable'; readonly label: string }
   | { readonly mode: 'unknown'; readonly label?: string });
```

**没有 `resolveName`**（asar 里 `resolveName` 的 5 处命中全是 fast-xml-parser 的 `_resolveName`）。

**结论**：反馈人给的 `ctx.subagents.resolveName(caller, name)` 是 **0.2.2 才有的**。在这台 0.2.1 机器上，名字→会话 id 的反查只能用 `listChildren(parentSessionId)` 扫 `label`。

### 2.6 `ctx.agents` 只按 session id 索引

插件里三处在用 agent 名字查：
- `index.js:600`（`task_describe` 的探活）
- `index.js:774`（`task_append_message` 的投递）
- `index.js:1027`（启动对账探活）

按名字查必然 `undefined` → 探活恒假、追加恒 undeliverable、对账恒 lost。

## 三、按兼容层任务书重新组织

任务书的核心命题是：**版本号不能代替能力检测；差异集中在 Adapter；不支持必须明确降级，不得伪造。**

把两份反馈映射进这个框架，看哪些是「版本差异」，哪些是「纯 bug」，哪些是「能力缺口」：

### 3.1 分类

| 现象 | 属于兼容层的哪一类 | 处理方式 |
|---|---|---|
| `jobs.start` 参数量变了 | **版本差异**（0.2.2 起强制 `spec.owner` 解析活 agent） | Adapter 内归一；已有代码按新契约写，旧版兼容 |
| `kill`/`readAt`/字段名 | **版本差异** | 同上 |
| `subagents.resolveName` 有/无 | **能力差异**（`capability: subagent.resolve_name`） | 三态检测；`unknown`/`unsupported` 时降级到 `listChildren` |
| `subagent/end` 认不出任务 | **纯 bug**（匹配逻辑漏字段） | 直接修，与版本无关 |
| `ctx.agents.get` 按名字查 | **纯 bug**（索引语义用错） | 直接修 |
| 结算兜底探活 | **降级策略**（事件可能丢） | 按任务书 §8「事件订阅 → 受控轮询」写 |
| README 表述 | **文档** | 直接改 |

**关键判决**：`#2` 的三条里，**只有 `resolveName` 那一条是真正的版本问题**，其余两条是代码写错了——不该拿「兼容层」当挡箭牌。修 bug 优先于建 Adapter。

### 3.2 能力清单（本项目实际需要的，不是任务书的全集）

任务书 §5.2 给了 10 项能力标识。按本插件真实依赖收窄成下面这 7 项，每项都对应已在代码里出现的调用：

| 能力 ID | 宿主接口 | 0.2.1 状态 | 0.2.2 状态 | 检测方式 |
|---|---|---|---|---|
| `job.start` | `ctx.jobs.start(spec)` | supported | supported（`spec.owner` 必填） | 反射 `typeof start === 'function'` |
| `job.inspect` | `ctx.jobs.get/readAt` | supported | supported | 同上 |
| `job.cancel` | `ctx.jobs.kill(id, caller, reason)` | supported | supported | 同上 |
| `job.settle_event` | `ctx.jobs.events.subscribe({owners})` | supported | supported | `typeof events?.subscribe` |
| `subagent.resolve_name` | `ctx.subagents.resolveName(caller, name)` | **unsupported** | supported | 反射 + 试用一次 |
| `subagent.list_children` | `ctx.subagents.listChildren(parentId)` | supported | supported | `typeof listChildren` |
| `agent.get` | `ctx.agents.get(sessionId)` | supported | supported | `typeof get` |

补充：`ctx.workingDirectory.ensure`、`ctx.sandboxPolicy.resolve`、`ctx.sandbox.confine`、`ctx.systemPrompt.section`、`ctx.systemPrompt.getSectionOrder`、`ctx.tools.register`、`ctx.on` —— 0.2.1 全部实测存在（asar 命中数分别为 131 / 162 / 27 / 367 / 47 / 8 / 大量），暂不需要降级，但要进启动自检的清单。

### 3.3 兼容层的最小实现形态（不建独立 SDK 仓库）

任务书 §5 给了一个完整 SDK 目录树。**本项目不适合照搬**，理由：

- 任务书 §6 列了 6 个 Service、§13 要求维护兼容矩阵、§15 分了 P0–P6 六个阶段——那是给「多个插件共用一层」准备的。
- 现在只有两个插件（QQ Bridge 在本机是 dsh-world 内的模块，不是独立插件；协调器是唯一的独立插件）。
- 任务书 §3.2「不要为了抽象而抽象」、§18.6「统一接口应来自两个或更多插件的真实共同需求」——按这条自己的原则，现在只有 1 个消费方，**不建独立 SDK**。

**采用「插件内 compat 模块」形态**，满足任务书的核心要求但不引入第二个仓库：

```
background-task-coordinator/
├─ index.js                 ← 业务逻辑（tool 注册、状态机、通知）
├─ compat/
│  ├─ capabilities.js       ← 能力检测（三态）
│  ├─ jobs-adapter.js       ← ctx.jobs 的归一（含旧版签名兜底）
│  ├─ subagents-adapter.js  ← 名字→id 反查（resolveName | listChildren 双路）
│  └─ report.js             ← CompatibilityReport（启动自检输出）
```

对应任务书的映射：

| 任务书要求 | 本项目落点 |
|---|---|
| §5.1 Runtime Detector | `compat/report.js` 读 `ctx.constructor`/`process.versions`，读不到就 `null` |
| §5.2 Capability Detector | `compat/capabilities.js`，三态 + `source` + `confidence` |
| §5.3 Adapter Registry | **不需要**（单版本目标，不选适配器，只做能力分支） |
| §7 `Result<T>` + 错误码 | **不需要**（插件内部调用，不需要对外契约层；用现有 `{ok,text}` 形态） |
| §8 降级策略 | `compat/subagents-adapter.js` 的双路反查 + `task_list` 兜底探活 |
| §9 兼容性报告 | `compat/report.js`，启动日志一行 JSON |
| §16 性能与安全 | 能力检测只在 `apply()` 时跑一次，缓存到模块变量 |

**明确不做**（对应任务书 §18.6「不要为了抽象而抽象」）：
- 不建 `dsh-compat-sdk` 独立包
- 不实现 `SessionService`（插件不需要创建会话）
- 不实现 `UIService`（插件没有设置页）
- 不实现 `MessageService.writeAssistantMessage`（0.2.1/0.2.2 都没有可靠写入接口，按任务书 §6.4 必须报不支持——本插件也不需要）

## 四、要做的改动（按优先级）

### P0 · 修 `#2` 的三条真 bug（不依赖兼容层）

**P0-1 `subagent/end` 匹配补 `nativeSessionId`**

`index.js:1068`：
```js
// 现在
const t = d.listTasks({ limit: 500 }).find((x) => x.nativeId === String(id));
// 改成
const sid = String(id);
const t = d.listTasks({ limit: 500 })
  .find((x) => x.nativeId === sid || (x.nativeSessionId != null && x.nativeSessionId === sid));
```

**P0-2 `register_delegation` 反查真 session id**

改为双路：

```js
async execute(args, exec) {
  // ...
  const agentName = String(args?.agentId ?? '');
  const given = String(args?.sessionId ?? '');
  const realSid = await resolveSubagentSessionId(ctx, agentName, exec?.agent, given);
  d.updateTaskFields(tid, {
    status: 'running',
    nativeId: agentName,
    nativeSessionId: realSid ?? null,
    currentStage: 'delegated',
    updatedAt: Date.now(),
  });
  // 返回文本按解析成败分两种措辞
}
```

`resolveSubagentSessionId` 的双路（`compat/subagents-adapter.js`）：

```js
export async function resolveSubagentSessionId(ctx, agentName, callerAgent, given) {
  if (!agentName) return null;
  // 调用方明确给了、且不等于名字 → 直接用
  if (given && given !== agentName) return given;

  let sub = null;
  try { sub = typeof ctx.get === 'function' ? ctx.get('subagents') : ctx.subagents; } catch { /* 无服务 */ }
  if (!sub) return null;

  // 0.2.2+：按名字解析
  if (typeof sub.resolveName === 'function' && callerAgent) {
    try {
      const sid = await sub.resolveName(callerAgent, agentName);
      // resolveName 对「不是名字的 token」会原样返回，相等即未解析
      if (sid && String(sid) !== agentName) return String(sid);
    } catch { /* 降级到 listChildren */ }
  }

  // 0.2.1：扫父会话的子级目录，按 label 匹配
  if (typeof sub.listChildren === 'function' && callerAgent?.session?.id) {
    try {
      const kids = await sub.listChildren(callerAgent.session.id);
      const hit = (kids ?? []).filter((k) => k?.label === agentName);
      if (hit.length === 1) return String(hit[0].id);
      // 多个同名：取最新那个（createdAt 最大），并标注不确定
      if (hit.length > 1) {
        hit.sort((a, b) => (b.createdAt ?? 0) - (a.createdAt ?? 0));
        return String(hit[0].id);
      }
    } catch { /* 拿不到就 null */ }
  }
  return null;
}
```

**注意**：`label` 是否等于 `agentId` 需要实测验证。原生 `subagent` 工具返回 `started subagent my-agent`，`label` 应由同一来源写入——但这条**尚未在真机验证**（本机没法起真 subagent 做端到端）。文档里标注 `unverified`，改完必须实测。

**P0-3 三处 `ctx.agents.get` 换 id**

```js
// 三处统一成
const sid = t.nativeSessionId || t.nativeId;
const ag = sid ? ctx.agents?.get?.(sid) : undefined;
```
落点：`index.js:600`、`774`、`1027`。

### P1 · 结算兜底（对应任务书 §8「事件订阅 → 受控轮询」）

`task_list` / `task_describe` 执行时顺带扫一遍活动中的 subagent 任务：

```js
// 只对「能解析出真 session id」的行动手，解析不出的不动
for (const t of activeSubagentTasks) {
  if (!t.nativeSessionId) continue;
  if (ctx.agents?.get?.(t.nativeSessionId)) continue;
  // 原生已回收但没收到 end → 补落 lost
  d.updateTaskFields(t.id, {
    status: 'lost',
    errorSummary: '原生 subagent 已回收，但没收到 subagent/end',
    updatedAt: Date.now(),
    completedAt: Date.now(),
  });
  emitEvent(null, t.id, 'task.lost', 'reconciler', '探活兜底');
  settleNotification(null, { id: t.id, status: 'lost' });
}
```

限制：只在工具调用时触发，不额外开定时器（任务书 §16「不得高频执行昂贵探测」）。
