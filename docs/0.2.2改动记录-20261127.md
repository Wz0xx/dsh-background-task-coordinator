## 一、`taskkill` 同步阻塞宿主（P1-2 残留）

```js
// 0.2.1 及以前
execSync(`taskkill /T /F /PID ${child.pid}`, { stdio: 'ignore' });
```

`execSync` 会**阻塞宿主事件循环**。杀一棵大进程树能卡住几百毫秒，期间整个 DSH 都不响应——等于在一个「取消」动作上卡住前台。

改成异步 `spawn`，`stdio: 'ignore'` + `unref()`，不等结果：

```js
const killer = spawn('taskkill', ['/T','/F','/PID', String(child.pid)], {
  windowsHide: true, stdio: 'ignore', windowsVerbatimArguments: false,
});
killer.on('error', () => {});
killer.unref();
```

杀进程本来就不需要在当前栈上等结果。顺带把 `execSync` 从 import 里去掉了。

**注意这里的 `windowsVerbatimArguments: false`**——和 0.1.9 那个坑相反：那条是「我们自己拼的 `cmd /d /s /c <原文>`」必须 verbatim，这里是「独立 argv 调用、没有引号拼接」，必须让 Node 正常转义。同一个选项在不同上下文里答案相反，不能一刀切。

## 二、首行为空的 objective 未拦截（P1-2 残留）

`objective` 写成 `"\nnpm test"`（前面带个换行）时，`firstLine` 是空串，于是 spawn 一条空命令：子进程立刻退出、台账落 `failed`，而模型以为命令在跑。

现在拦在建任务之前，明确告诉调用方第一行必须是什么：

```
建任务失败：objective 的第一行是空的。type=job 要求第一行必须是可执行命令
（比如 `npm run build`），注意别在命令前留空行或换行。（taskId=…）
```

首行全是空白也走这条。

## 三、`sweepOnce` 单次 miss 就判死（P2-1）

**这条是真正的「数据不可逆」问题。** `ctx.agents.get` 有瞬时查不到活 agent 的时候（注册表切换、宿主忙），而 `lost` 在 `TERMINAL` 里、不可逆——一次抖动就能把正在跑的任务打死，且没有任何补救。

改成**连续两轮都查不到才认**：

```js
const MISS_THRESHOLD = 2;
const missStreak = new Map();   // taskId → { n, last }

// 查到 → clearMiss；查不到 → bumpMiss，n < 2 就先不动
```

中间只要有一轮查回来就清零。探活**抛异常**（不是返回 undefined）仍然按「这轮不下结论」处理，直接 `continue`——那是「没问成」，比「问到了没人」更不该下判断。

内存态、进程重启就清空，这是刻意的：重启后由「启动对账」统一裁决，不该带着上一个进程的怀疑继续算。

验证：`flaky` 用例（第一次 miss、第二次查到）保持 running；持续 miss 的用例第一轮不动、第二轮落 lost。

## 四、Mode B 秒结竞态（P2-3）

子代理可能在前台调 `task_register_delegation` **之前**就跑完——事件比绑定先到。以前这里直接 `return`，事件被丢掉，那条任务就永远停在 `running`，等一个已经发生过的结束事件。

这不是异常路径：短任务（"回两个字"这种）几乎必中。

改法：

1. 匹配不上时把事件缓存进 `earlyEnds`（key = 会话 id，10 分钟过期）
2. `task_register_delegation` 绑定成功后查一次，命中就**回放**

回放走的是同一个 `settleFromSubagentEnd()`——不是为了少写几个字，是因为 stopReason 映射是「假成功/假失败」的分界线，两份实现迟早会漂开。

返回文案也跟着改：回放过就不再嘴硬说「任务进入 running」。

```js
const head = replayText
  ? `已绑定：task ${tid} ↔ agent ${agentName}。`
  : `已绑定：task ${tid} ↔ agent ${agentName}，任务进入 running。`;
```

验证：先发 `subagent/end` 再绑定 → 落 `succeeded`；`aborted` 的回放成 `cancelled`。

## 五、失联 job 无运行期恢复通路（P2-8）

`sweepOnce` 只管 subagent。job 的终态靠 `ctx.jobs.events.subscribe` 的 settled 事件，但那个订阅在某些宿主/版本上不存在，或者事件漏了——那样 job 会永远停在 running，永不超时、永不计入结算。

新增 `sweepJobsOnce()`：对活动中的 job 主动问一次 `ctx.jobs.get`：

| 原生状态 | 处理 |
|---|---|
| `completed` / `failed` / `killed` | 就地落账（与 settled 事件同一套映射） |
| 还在跑 | 清计数 |
| 查不到 / 抛错 | 连击计数，同 subagent 规则（连续两轮才判 lost） |

挂两个地方：`task_list`（用户主动看的时候顺带核实）+ 维护循环（没人看也会收）。

顺带删了一句假日志。原文：

```
ctx.jobs.onSettled 不存在——结算回收走 task_describe 的 readOutput 兜底，签名待实测
```

**根本没有什么 `readOutput` 自动补结算**——`readAt` 只是读输出，不会写台账。那句话会让读日志的人以为「反正有兜底」。改成实话：

```
ctx.jobs.events.subscribe 不存在——收不到结算事件；
job 的终态只能靠 task_list / task_describe 读时探活（见 sweepJobsOnce），不会自动落账
```

## 六、`task_context` 没有 `expectedVersion`（P2-5）

乐观锁一直在，但调用方没法指定「我基于哪个版本写」——于是两个代理各自读、各自写时，后写的静默覆盖先写的。

现在参数里加了 `expectedVersion`：

```js
// 带了就按它校验，不符直接拒
if (wantVersion !== null && wantVersion !== (ctxNow.version || 0)) {
  return { ok: false, text: `上下文版本冲突：你要基于 v${wantVersion} 写，但库里已是 v${ctxNow.version}。` };
}
```

不传仍可用（向后兼容），但那种情况下并发写会互相覆盖——这一点写进参数说明里了，不假装它能防并发。

验证：A 写 v1 → B 基于 v1 写成 v2 → A 还拿 v1 写被拒 → 读回来仍是 B 的内容。

## 七、`settleNotification` 只记账不投递（P2-9）

**这条我查了宿主的真实服务表再动手**（cordis inspect `listService` 全表），确认：

- 宿主**没有**通用的「发通知」服务（叫 Notification 的那几个都是 MCP 协议类型或账户奖励，无关）
- 但 `agents.get(sessionId)` 能拿到发起会话的活 agent，上面有 `followup`/`steer`——和 `task_append_message` 用的是同一条通道

所以通知 = 向 owner 会话投一条 user 消息，内容是终态摘要。三条约束：

1. **只投协调器自产、前台收不到的终态**（探活兜底 `lost`、重启对账 `lost`、超时清账）。
   原生 job/subagent 结束本来就会回到前台，再投一条是噪音。
2. **幂等**：同 `taskId + status` 只投一次。
3. **投不出去如实记**，措辞不许退回「已送达」。

为此加了模块级 `ACTIVE_CTX`（`apply` 注入、`dispose` 清掉），因为 `settleNotification` 是模块级函数、拿不到 `ctx`。

验证：

- 原生结算 → 0 条通知（不重复投）
- 探活兜底 lost → 真投到发起会话，事件流水写「已投递到发起会话」
- 再扫一轮 → 不重复投

## 九、还剩什么

核验报告列的问题里，这一版之后仍然存在的：

- **`cancel` 传 `keepInbox: true`** 偏「暂停」语义，未兜底 `interruptByParent`（需要真机确认语义，本机 0.2.1 上 `interruptByParent` 存在但参数含 `mode: 'continuable'`，不确定是否等价）
- **`sandboxed.env` 未透传**、无命令审批门（要改沙箱契约，风险大于收益）
- **`cancel_requested` 下收到 `stopReason='completed'` 仍判 cancelled**（A07 会合规则，是刻意的：协调器请求过取消，结束就算确认）
- **`sweepOnce` 的 miss 计数是内存态**，重启清零（如前述，刻意）
- **`task_list({all:true})` 的 `listRecent(50)` 未按 caller 过滤**（别的会话新建 50 条会挤空当前视图）

前两条我认为需要 0.2.2 真机或宿主契约配合，不宜盲改。
