## §1 `getAgentHandle` 三处调用里有两处空转 —— 已用 `toTaskHandle` 根治

### 反馈说的

`docs/0.1.5改动记录` §一.3 声称三处取 handle 都改成了 `getAgentHandle(ctx, t)`，
实际只有启动对账生效；`task_describe` 和 `task_append_message` 行为与 0.1.4 一样。

根因：`getAgentHandle` 靠 `nativeSessionId` 找 agent，而失效的两处传的是**手拼对象**，
只有 `nativeId`（agent 名），于是退回用名字查 `ctx.agents`（该表只按 session id 索引）→ 恒 undefined。

### 核实

确认无误。三处手工拼的 `t` 全部缺 `nativeSessionId`：

- `task_describe` 的 `t`（`id/conversationId/type/title/objective/status/nativeId/stage/...`）
- `task_append_message` 的 `t`（`id/type/nativeId`）
- `task_cancel` 的 `t`（`id/type/nativeId`）← 反馈额外点出的第三处

### 修法（按反馈建议的「根治」那条）

新增 `toTaskHandle(row)` 作为台账行 → 工具对象的**唯一入口**，四风字段一次给全：

```js
function toTaskHandle(row) {
  if (!row) return null;
  return {
    id: row.id,
    conversationId: row.conversationId ?? null,
    type: row.type === 'subagent' ? 'subagent' : 'job',
    title: row.title ?? null,
    objective: row.objective ?? null,
    status: row.status ?? null,
    nativeId: row.nativeId ?? null,          // agent 名
    nativeSessionId: row.nativeSessionId ?? null,  // 真会话 id（getAgentHandle 要用这个）
    stage: row.currentStage ?? null,
    // ... 其余字段
  };
}
```

改动点：
- `loadTasks()` 的投影改成 `{ ...toTaskHandle(t), version, context, messages }`（去重）
- `task_describe` / `task_append_message` / `task_cancel` 三处 `const t = {...}` → `const t = toTaskHandle(row)`
- `task_create` 里新建任务的初始化保留手写（那时还没有 nativeSessionId，是对的）
- `task_append_message` 成功文案补上会话 id：`已投递到 agent probe-a（会话 sess-A）`

### 验证

| 用例 | 结果 |
|---|---|
| `task_describe` 查活着的 agent | ✅ 输出 `原生 agent：keys=status,followup,steer`（不再「查不到」） |
| `task_append_message` 投递 | ✅ 返回 ok，不再 `undeliverable` |

## §2 启动自检在 0.2.2 上恒 `degraded` —— 已改判定口径

### 反馈说的

`resolve_name` 与 `list_children` 是 OR 关系的一对手段，只要一条能用就不算降级。
0.1.5 把「任何一项 unsupported」都算 degraded，而 0.2.2 上 `list_children` 必然 unsupported
（它是模块级函数不是服务方法），于是恒定 degraded —— 永远亮的告警等于没有告警。

### 核实

确认。0.1.5 的 `degraded` 计算是：

```js
const degraded = Object.entries(caps).filter(([, v]) => v !== 'supported').map(([k]) => k);
```

还把单独算出来的 `settle_resolve` 混进去，导致自检报告自己跟自己矛盾。

### 修法

1. `caps` 每项改成 `{ status, required }` 结构，`required` 标记哪些缺了就不能用
2. `degraded` 只算「非必需且确实缺」的
3. `resolve_name` / `list_children` / `settle_resolve` 作为一个 OR 组整体判定：
   只要有一条能用，整组不计入 degraded
4. 给所有能力探测加 `has()` 护栏 —— 读属性本身也可能抛（受控代理），
   一项抛不该拖垮整份报告（反馈点出的 `sandbox.policy` 疑问）
5. 报告加 `requiredFlags` 字段，人一眼能看出哪些是必需的

### 验证（五种宿主形态）

| 场景 | 结果 |
|---|---|
| 0.2.2（有 resolveName、无 listChildren） | ✅ `compatible`，degraded 为空 |
| 0.2.1（有 listChildren、无 resolveName） | ✅ `compatible`，degraded 为空 |
| 两者都无（真降级） | ✅ `degraded` |
| 缺 `job.start` | ✅ `incompatible` |
| `sandboxPolicy` 读属性抛错 | ✅ 仍有 `compat:` 行，不落 catch |

## §3 文档说探活在 `task_list` 与 `task_describe` 都触发，代码只有一处 —— 已对齐

### 反馈说的

同一篇 0.1.5 文档自相矛盾：§三标题写「只 `task_list`」，§八未验证项却说两个都触发。
代码只有 `task_list`。

### 修法

按反馈建议的第一个方案（抽函数，两处都调）：

```js
function sweepOnce(d) {
  let swept = 0;
  for (const t of d.listTasks({ limit: 500 })) {
    if (t.type !== 'subagent' || !ACTIVE.has(t.status) || !t.nativeSessionId) continue;
    if (getAgentHandle(ctx, t)) continue;
    // 原生已回收但没收到 subagent/end → 补落 lost
    swept += 1;
  }
  return swept;
}
```

- `task_list`：扫完再列，输出「（本轮探活补落 N 条 lost）」
- `task_describe`：**先扫再读**，输出同样带补落提示

同时在 `docs/0.1.5改动记录-20261127.md` §三加了补记，说明原文档那处矛盾已在 0.1.6 校正。

### 验证

| 用例 | 结果 |
|---|---|
| 只调 `task_describe` 查已回收任务 | ✅ 状态补落 `lost`，输出带「探活补落」提示 |

## 仍然未验证的

1. **`listChildren` 返回的 `label` 是否等于 agent 名** —— 0.2.1 反转查的地基。
   若不等，0.2.1 上反查失败、结算退回探活兜底（不假成功，但会迟一步）。
2. **0.2.2 的 `resolveName` 真实签名** —— 反馈说 `resolveName(caller, name, signal)`，
   带 signal；0.1.6 的调用是 `resolveName(caller, name)`，不传 signal。
   如果宿主强制要求 signal，这里会抛 → 落到 listChildren 分支（0.2.2 上该分支不存在）→ 返回 null。
   **这条建议实测确认**。
3. **`subagent/end` 的 `id` 是否等于 `listChildren` 的 `id`** —— 类型都是 SessionId，理应相等。
4. **探活只在工具调用时触发** —— 不调 `task_list`/`task_describe` 就不会自动落 `lost`。
   这是有意的（任务书 §16 不得高频探测），但用户要知道。
