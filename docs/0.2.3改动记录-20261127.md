## 一、GBK 解码器的两个边界（它抓到了我的真 bug）

这是本版最有价值的一条。我 0.2.2 的解码器有两个破口，都实测复现：

### ① 积压字节存在时，纯 ASCII 段会旁路

```js
// 0.2.2
let hasHigh = false;
for (const byte of b) { if (byte >= 0x80) { hasHigh = true; break; } }
if (!hasHigh) return b.toString('utf8');   // ← 没看 pending 里有没有东西
```

GBK 的**次字节可以落在 ASCII 区**（0x40–0x7E）。比如「丂」= `81 40`：

```
chunk1 = 81        → 非 ASCII，进 pending
chunk2 = 40 0A     → 纯 ASCII → 直接吐出去，pending 里的 81 还在
```

结果：字被劈成两半，且顺序错乱。实测旧实现输出 `"@\n�"`。

### ② `end()` 对残留字节硬走 UTF-8

```js
// 0.2.2
const rest = takeAll();
return rest.length ? rest.toString('utf8') : '';
```

「A中」= `41 D6 D0` 一次给完时，`sniff()` 因为「尾部截断保护」判断不了（D6 D0 可能是个被截断的 3 字节序列），返回 `null`，数据全留在 pending。流结束时到这里，直接 `toString('utf8')` → 输出 `"A��"`。

### 改法

```js
// ① 只有没积压时才允许 ASCII 快路
if (pendingLen === 0) { ... if (!hasHigh) return b.toString('utf8'); }

// ② end() 严格试一次，过不了就 gbk
try { enc='utf8'; return new TextDecoder('utf-8',{fatal:true}).decode(rest); }
catch { enc='gbk'; return new TextDecoder('gbk').decode(rest); }
```

我把 0.2.2 的旧实现单独抄出来跑，确认两个用例都乱码（`"@\n�"` 和 `"A��"`），修完分别是 `"丂\n"` 和 `"A中"`。**不是靠读代码觉得有问题，是先复现再改。**

## 二、`resolveSubagentSessionId` 的两处漏网

我 0.2.1 加过「`given` 不能随便信」的判断，但有两条没盖住：

**① 占位字面量能过检查。** `"current"`、`"undefined"` 这类词长度够、无空格、非中文，全都能通过我那条粗糙的「像不像 id」判断。而 `current` 恰好是 `task_create` 的 `conversationId` 默认值，最容易混进来。

**② 父会话 id 会被当成子会话 id。** 把父 id 落进 `native_session_id` 之后，这个任务永远匹配不上真正的 `subagent/end`（事件带的是子会话 id）。

它还把 `parentSid` 的计算提到了函数开头——因为第 ② 条的自指检查需要它，而 0.2.2 是在下面的 `listChildren` 分支里才算的。

## 三、`sweepOnce` 跨会话写别人台账

这条对应我自己在 0.2.1 文档里记的残留：「`task_list` 的 `sweepOnce` 仍跨所有会话扫描并写终态」。

A 会话调一次 `task_list`，就可能把 B 会话的任务标成 `lost` —— 那是**写别人的台账**。它给的修法很直接：传 `caller` 进去，只探活自己的。

```js
if (caller && t.ownerSessionId && String(t.ownerSessionId) !== String(caller)) continue;
```

同时把返回值从数字改成 `{ swept, suspects }`，让 `task_list` 能说清「有条第一次没命中、再查一次才落终态」——不然两轮阈值看起来像个不透明的延迟。

## 四、`listRecent` 没按 caller 过滤

我自己在 0.2.2 结尾提过的那条小 bug：`task_list({all:true})` 取「最近 50 条」时没传 caller，别的会话新建 50 条就把当前会话的历史视图挤空。它一并修了，我采纳。

---

## 五、`cancel` 的 `keepInbox` 语义

我 0.2.2 传的是 `keepInbox: true` —— 那是**暂停**语义：队列留着，之后还能被 `followup` 唤醒继续跑。

而 `task_cancel` 是**取消**：用户说不干了，就不该把排队中的指令留着。改成 `false`。

同时它补了兜底：agent 句柄没有 `cancel` 方法时，退到 `ctx.subagents.interruptByParent(childSessionId, parentSessionId, 'continuable')`。这个方法我在 0.2.2 的「还剩什么」里点名过，因为不确定 `mode` 参数的语义而没敢改 —— 它直接用了，而且 `mode: 'continuable'` 确实是本机唯一的取值（cordis inspect 查过签名）。

---

## 六、二次登记保护 + 启动对账不误判

**二次登记**：对已在 `running`/`cancel_requested` 的任务再调 `task_register_delegation` 换一个 agent，等于把任务绑到别处——之后 followup / 结算 / 取消全落到新目标，原来那个还在跑。现在拒绝，并且不拒绝「同一个 agent 名补全 session id」这种情况。

**启动对账**：探活**抛异常**时判 `lost` 是错的。那是「没问成」不是「问到了没人」。外面那层 `catch { alive = false }` 会把异常直接当死，重启一次全标 lost——和我 0.2.1 修的三处崩溃点是同一类错误。现在单独接，按「暂不判断」处理。

---

## 七、`sandboxed.env` 透传

`sandbox.confine()` 的返回可以带 `env`，那通常是沙箱自己设的隔离变量（HOME/TMPDIR/PATH 重定向）。只吃 `argv` 不吃 `env` 是**半套隔离**：命令在沙箱里跑，环境看着还是宿主那一套。

现在合并方向是「宿主 env 作底、沙箱覆盖在上」，没有 `env` 时不传这个键（避免无谓地复制一大份环境）。

顺带一条它提的：`ctx.jobs.kill()` 可能在同一调用栈里同步触发 settled 回调，那条路径已经把任务落成 `cancelled` 了。我原来的取消路径会再写一遍，导致重复发事件、并且在新状态上覆盖 `errorSummary`。现在写之前重读一次，已终态就跳过。

## 没采纳的

| 它的做法 | 为什么不跟 |
|---|---|
| `settleNotification` 仍只记账 | 我 0.2.2 已经改成真投递（`agents.get(owner).followup`），比它更进一步 |
| 没有 `sweepJobsOnce` | 我 0.2.2 新增的 job 探活它没有，那解决的是「结算事件根本不存在」的宿主 |
| 没有 `expectedVersion` 冲突的显式提示 | 它加了参数但冲突文案比我简略 |
| 把 `db()`/`emitEvent`/`settleNotification` 全挪进 `apply` | 这个思路对（解决模块级单例在多实例/热重载下互相覆写），但改动面太大、风险集中。我记进「待办」，不当场做 |
